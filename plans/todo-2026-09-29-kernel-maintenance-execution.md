# 内核有界维护执行重构

状态：**内核自主推进的责任边界已确认，执行方案待细化，未实施**。用户正常调用/观察，不需要特殊 syscall、显式让出或专用用户进程来提供内核执行机会。队列布局、工作原语与份额算法尚未达到施工门。全项目范围与已确认的 Close 语义由[设计总纲](todo-2026-09-29-system-redesign.md)拥有，本案只拥有必须由内核推进的有界执行，不拥有对象业务状态。

## 目标、边界与当前事实

目标：Close、终止、已提交映射修改及其回滚/退休不依赖调用者继续 syscall；每次不可抢占推进有结构上界，连续维护不饿死用户线程、期限和远端确认。相同承载可用于经过准入的批量分配准备，不能为分配和释放各造一套执行系统。

现有 `os/kernel/src/{deferred_work,work_ledger,remote_call,sched,trap}.rs` 与 `task/{notify_work,request,retirement}.rs` 分担预算、执行队列、依赖及收尾。`sched.rs::run` 在 pick 前推进维护，`idle` 检查待办后才睡眠；因此“没有用户线程就没有内核执行机会”不成立。当前多类 debt、ProcessDrain request 和 WaitSet 专门 actor 不作为目标结构。

非目标：业务任务 executor、用户回调、文件系统政策、任意 kernel thread 框架。保留协作式执行是本轮推荐前提；若改为可抢占/可睡眠内核，必须另行闭合全套执行与锁语义，不能在本案顺手加入。

## UnitOfWork 的机制定位

本轮进一步提出：将必须续跑的特权责任称为内核 UnitOfWork。它是持有资源与显式进度的无栈工作拥有体；Process 回收是一个消费者，不能把该机制定义成 ProcessDrain 的换名。名称暂不冻结 Rust 类型或模块。

公共机制拥有：稳定执行根、独占推进、工作额度、Ready/Blocked/Done、依赖唤醒和完成交接。对象类型拥有其领域状态及每一步实际动作。每批运行复用既有工作记录，不为每个资源条目创建独立 task，也不将任意闭包或用户 callback 引入内核。

除进程外，持久订阅集合退休、宽映射/页表退休、能力级联以及未来 MMIO/IRQ/DMA 绑定撤销都可能需要同一执行契约。`task/retirement.rs::drain_current` 与 `deferred_work.rs::drain_current` 已有非 ProcessDrain 的分步消费者，证明需求并非仅为未来假设；它们的现有形状不作为必须保留的目标。

## 容量约束与单步约束

不能为了使整体释放一次完成，任意限定每个进程只能持有很少资源、或强迫大对象拆成许多小对象。总工作可以随资源规模增长，由 UnitOfWork 持续推进。

仍需保留实际约束：物理资源与 metadata 准入、authority 和付款边界、在途责任存量，以及每一步不可抢占工作的结构上界。UnitOfWork 不消除成本，也不能把内部仍做完整遍历的函数包装成一个合格 step。

如果某个底层动作本身不能分步且没有可接受的执行上界，需要改写原语、转成发起/完成协议，或明确重审执行模型；不能以它位于维护队列中为理由接受任意长执行。
## 推荐执行形状

### 稳定责任与三个推进结果

每一份必须续跑的工作有一个稳定 owner，拥有资源、进度及完成责任；正常 Close、失败回滚、进程退出转交同一 owner，不建立第二份清理算法。

公共执行面只需表达：

- `Ready`：仍有可执行步骤；本轮按额度运行，未完成重新排到公平队尾。
- `Blocked`：缺少明确依赖；登记唤醒并退出 runnable 集合，禁止 timer 轮询模拟依赖完成。
- `Done`：所承诺的完成边界成立；归还执行承载并完成相应通知。

`Running` 是队列独占执行权，不是各对象复制的一层业务状态。一次只能有一个执行者推进同一 owner；唤醒与本轮完成竞争不能把它重复入队或丢掉下一轮。

固定上界的叶释放可以直接完成，不要求每次 Close 创建任务。需要分步的工作记录在责任产生前准备，队列挂接不分配；释放最后 capability 不应临时申请一个可失败的工作槽。新的修改若增加未来清理负担，在该修改提交前扩充准入。

### 执行点与公平

推荐将共同维护入口放在 hart 的安全出口与调度循环。业务锁全部释放后才进入；只有取得本轮维护执行份额才推进，随后重新检查调度及 pending 来源。执行位置不等于优先级。

```text
服务 pending 中断/期限/远端确认
→ 有维护份额时执行一轮有界维护
→ 有 runnable 用户线程：调度并返回用户态
→ 无用户线程但有 Ready 维护：返回循环边界继续
→ 只有 Blocked 维护：确认依赖唤醒已登记后才可 idle
```

连续维护期间也必须检查到期计时器和新 runnable 工作，不能把这些检查只放在用户 trap 或 WFI 醒来分支。可运行维护不得因本轮预算耗尽而永久入睡；等待依赖的维护不得空转耗尽 CPU。

公共层拥有 Ready/Blocked/Done 的仲裁、预算和唤醒；各资源类型只提供有界 step 及依赖事实，不再各写不同的“公平轮询 + 重试 timer + 清理队列”。不同紧急程度的远端确认与普通回收可有执行优先关系，但它必须有饥饿边界，不能用无限高优先级回收占满安全点。

多个进程持续产生工作时，单个对象不能靠无限排队项取得不成比例的执行机会。准入约束未完责任的存量，调度规则约束各拥有域的进度；两者分别设计，不以“有上限”代替公平。

维护与用户执行的份额必须跨 syscall/trap/idle 等入口统一核算，不能每到一个安全点就重新发放完整维护预算。长期有用户负载时维护仍需保证进度，维护持续就绪时用户也需取得执行；只有 idle 有空才处理与每次入口排空队列都不满足要求。无用户 runnable 时可使用空闲执行能力，但仍在每批之间服务期限和远端依赖。执行费用不能无条件归到恰好触发下一次 trap 的无关进程。

### 与内核线程的区别

| 维度 | 本案的无栈 UnitOfWork | 通常的可阻塞内核线程 |
|---|---|---|
| 持久现场 | 显式字段、资源 owner 和下一步状态 | 独立栈、寄存器现场和调用链 |
| 等待 | 登记依赖后 step 返回，随后重入 | 挂起执行上下文，醒来继续调用栈 |
| 让出点 | 每个受审计的有界 step 结束 | 线程调度/阻塞点；是否可抢占取决于内核模型 |
| 调度关系 | 内核维护执行类别，明确份额与公平 | 线程调度实体，优先与份额由调度政策决定 |

广义上 UnitOfWork 确实是内核内调度的任务，不应以“没有线程”声称没有调度复杂度。选择无栈形态是为了保持协作式内核的显式让出、锁外推进和有限栈要求；并不意味着维护天然最高优先级。必要的短小中断/远端响应与普通资源退休必须分别论证执行优先和饥饿界。

### 唤醒与 owner 消散

- 工作发布与其执行根同时成立；Close 返回前责任已经可达，不能留给被释放的用户帧补发布。
- 依赖登记采取登记与复检的协议，避免“依赖已完成但尚未登记”的丢唤醒窗口。
- 跨 hart 发布先使队列/状态可见，再通知执行 hart；入睡方登记 idle 后复检。门铃只是提示，Ready 状态是真值。
- 调用者死亡只能取消交付或观察，不能取消已提交工作。未提交准备的取消也由原准备 owner 收束，不产生无人回滚的资源。
- 工作 owner 不依赖它正在释放的对象观察者来推进，禁止自己等自己或相互订阅形成完成环。

## PM 与设备管理的责任边界

PM 持有监督和终止政策，发起终止并观察资源收束；内核持有终止被接受之后的特权推进责任。把 PM 定为必须存活的可信回收执行者可以形成另一种一致的系统契约，但会让其存活成为回收活性前提；当前已选择自动回收，因此不再要求 PM 代跑 UnitOfWork。这里不删除用户态服务内部业务善后的责任。

设备侧的潜在消费者包括 MMIO 绑定的 CPU 映射撤销、IRQ 订阅/路由解绑与迟到事件收束、以及有平台保证的 DMA 映射撤销和同步。各自资源对象持有独立工作根，不能全部寄生于驱动 Process 回收：设备工作可能在进程退出后仍有未完成的硬件使用。

通用执行器不理解驱动名字、寄存器脚本、设备选择、业务排空或复位政策。已经提交的特权撤销由内核独立推进；用户态驱动/可信恢复 provider 提供其负责的硬件协议与完成事实，设备管理者协调不同资源与供应关系。具体硬件依赖按设备分案固定规范取证，本案不预设 IRQ、DMA 与 CPU 撤销的一套通用顺序。

驱动进程消失、CPU 映射撤销、硬件 DMA 已停止是不同事实。无可验证的停止/隔离证据时，相关 backing 继续由隔离责任保活，不退款、不复用。维护应停驻或报告明确的隔离结果，不能高优先级忙轮询，也不能用超时或已处理全部工作批次伪造安全完成。Close 的必成本地交接不等于故障硬件最终一定允许物理回收。

## 先减少总工作，再对剩余工作分步

1. **整拥有体释放**：保存真实拥有链和根，不在关闭时从全局表搜索“属于谁”。摘根可很短；子项的独立资源仍需逐项正确终结。
2. **释放不重新组装分配事务**：完整 mapping/对象关闭优先直接转交已持有的 ledger/backing/退休状态，不在关闭时重新拆大页、申请分片和资金。部分区间修改是另一个可拒绝操作。
3. **进程整体退休**：执行与已提交使用屏障达成后，使整个地址空间进入独占退休；不用针对每个区域重演 Running Unmap 的授权、竞争与同步协议。
4. **合并确认与退款批次**：可以合并同一地址空间/代次的失效，按真实 extent 释放物理库存；不能跨资金来源或共享 owner 伪合并。
5. **限制级联栈深**：最后引用触发新的收尾时移交工作，不递归释放任意深度对象图。

批量 free、页链归还、arena reset 可以减少管理工作，但不能抹掉共享引用、副作用通知和安全清零。延迟清零只是把成本移到再分配，必须在那里计入预算。

## 分配与回收的不同失败边界

| 操作 | 可失败时点 | 成为长工作时 |
|---|---|---|
| 普通新建/扩大资源 | authority 校验和准入阶段可以拒绝 | 内核持准备 owner 分批清零/建表；未成功发布前可取消并收束准备 |
| 合法 Close/已拥有资源完整释放 | 不因清理容量或临时繁忙拒绝 | 使用之前准入的状态，转交内核继续推进 |
| 部分修改/业务事务 | 在其明确提交点之前可拒绝 | 提交后由稳定 owner 完成，不返还伪造的可重试输入 |

大分配是单次请求的多步内部执行，还是由资源接口天然限制单次规模，必须由实际资源模型决定；不能用无依据的“小常量”把工作拆分责任推给所有用户。

## 迁移面与删除门

- `sched/trap/remote_call`：统一服务 pending 与维护的执行入口，接通无用户线程、timer 到期和跨 hart 唤醒。
- `deferred_work/notify_work/request/retirement/work_ledger`：盘点哪些状态是领域事实、哪些只是重复执行机械；机械归并后删除旧队列/轮转/重试，不能在现有各队列外再包一层总调度器。
- `task` 与内存事务：每个可延续 owner 注册唯一执行责任，处理正常、取消、关闭与退出；移除调用者必须再次 syscall 的推进协议。
- 公共 ABI 不提供 step、预算或内部游标；用户只表达业务意图或等待明确完成事实。

本案不能在没有真实消费者接通时宣称系统级活性已经完成；可以先完成执行机制自身契约，但须明确剩余消费者。

## 施工前设计门

尚需确定：队列存储与所有权布局、工作记录准入来源、hart 归属与迁移规则、依赖登记 API、各工作原语的结构成本、跨 owner 公平算法，以及不同完成类别的优先与饥饿上界。上述选择须落实到类型、锁序及并发时序后才可开工；本轮示意不是通用 trait 的最终签名。

## 验证

- 无 runnable 用户线程时，多批释放最终完成；其间 timer 唤醒的新线程获得调度。
- 多个拥有域持续产出工作时都有进度；单一巨大对象不会垄断执行。
- 依赖在登记前、登记中、刚停驻后完成均不丢唤醒；重复唤醒不重复执行 owner。
- 准入已经用满后合法释放仍可发布；队列承载不会向关闭方返回 OOM/Busy。
- 调用者与观察者全部消失后工作根仍在；零引用级联不增长到无界内核栈。
- 清零、PTE 操作、扫描与最后引用回调计入实际预算，不以一次函数调用冒充常数工作。

使用项目已有 host 和 QEMU 设施；实现闭合后按 BUILD-AND-TEST 执行规定检查及相关组合路线。当前仅设计，无执行验证证据。

## 接力

内核自主推进方向已确认。下一步闭合施工前设计门，与 capability 释放和进程自动回收共同接通；用户态不提供特殊推进调用。具体工作表示、份额和队列仍待定型，ideas 的清理不能替代这些设计。仅把旧债务改名，或只增加一个外层 executor，不满足本案目标。
