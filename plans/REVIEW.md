# Review 纪律

> Review 只回过头看已经完成的任务，不在任务进行中插入；Review 不阻碍验收（设计确认 + 代码完成即验收通过）。本文只定义两类 Review 各自看什么。

## 设计 Review

对象是已完成实现背后的设计：`notes/ideas/`、活跃计划与相关 `notes/impls/`。回答一个问题——**这个机制本身合不合理**：

- 机制、边界、不变量与责任归属是否自洽、闭合，适合长期演进；
- 有没有更简单、更统一的做法——可合并、可简化、可重构的机会；
- 正常 / 失败 / 取消 / 并发 / 恢复路径是否同一机制，还是缝出来的特例；
- 内核与用户态边界是否合理，内核路径是否有界；
- ABI / 硬件 / 协议结论是否有规范或官方源码证据；
- 是否污染长期方向的临时机制、循环监督、双重真值、旁路 authority。
- 是否对某一对象进行特判、特殊处理，如果是，能否机制性重构改善。

## 代码 Review

对象是一个已完成、测试全绿的批次。三条轴：

1. **对 ideas 忠实**：代码是否实现了设计语义（生命周期、authority、契约）。
2. **对 impls 忠实**：代码是否实现了 impls 声明的实现机制——锁选型、锁序、所有权图、数据结构。发现更优机制选型时产出 impls 修订，而不是就地改代码。
3. **代码自身健康**（语言层面，以 Rust 为例）：
   - unwrap / expect 只允许结构性不可达且有注释论证；用户可达路径一律错误返回；
   - unsafe 逐处核对 SAFETY 论证成立；
   - 加锁前先问能不能靠结构消灭（单一所有权 / hart 私有 / 消息传递）；确需共享时选对锁、压短临界区、锁序单向成文；
   - 特殊分支与重复状态堆积 → 回设计层，标记设计反馈。

## 纪律

- 每条 finding 必须有证据：位置、可达性、违反的契约（ideas / impls / 语言层）；无证据的猜测不写，风格偏好不收。
- findings 集中修复，不修一条审一条；修复暴露架构选择时回到设计讨论。
- reviewer 用全新上下文（避免确认偏见），只报告不修改。
- 产物归属不变：方向进 ideas，实现事实进 impls，未完成行动进 todo，报告为 `review-<日期>-<主题>.md` 收口后归档。
