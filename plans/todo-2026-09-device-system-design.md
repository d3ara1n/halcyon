# 设备体系整体设计与逐层细化

> 状态：设计进行中，尚未达到施工条件。本记录是设备整体细化的唯一活跃入口，承接 [模块概念稿](archived/todo-2026-09-device-architecture.md)。当前只授权设计与文档，不实现 ABI、库、服务或驱动。

## 目标与当前承诺

以嵌入式 capability 微内核为前提，自顶向下覆盖设备体系及其与启动、内存、进程、服务发现、执行、预算和系统收束的接点。先确定全局一致的领域、authority、状态、生命周期、协议与运行拓扑，再形成能够据以施工的模块契约及依赖顺序。不以先跑通某个设备缩小设计范围，也不先实现若干局部机制后再拼接整体。

设计允许为后续能力铺路；不要求同时实现所有总线、设备类别和硬件平台。先用结构不同的场景检验通用边界，再界定首批实现能力。POSIX 兼容不在目标内；多用户非刚需，其未来政策留在用户态。

本轮产物是模块组织与设计路线，**不是完整详细设计完成**。首个驱动、具体平台、进程拆分、内核对象族和 wire 格式均未冻结。

基础机制与用户态分层按[全项目重构总纲](todo-2026-09-29-system-redesign.md)重新论证；旧分层计划和代码仅提供现状证据，不作为本篇必须沿用的前置结构。设备领域设计与内核对象、内存、IPC 设计相互校正，相关公共契约闭合后再实施。

## 设计轮次 2：内核维护与设备收束的接点

已确定普通 Close 是必成且不等待完整退休的本地释放，进程终止后的回收由内核自动完成。设备管理者仍拥有设备停止、恢复、重新分配和跨供应协调；进程终态不证明 IRQ/DMA/设备外部动作都已结束。

[内核 UnitOfWork 方案](todo-2026-09-29-kernel-maintenance-execution.md)可承载 MMIO 映射撤销、IRQ 解绑与迟到事件收束、DMA 映射/翻译同步等已提交特权责任。该方案尚待执行份额与具体承载闭合，本案不复制执行器；设备资源 owner 独立于驱动 Process，不能把驱动退出作为唯一维护入口。

D2/D4 须明确各操作依赖的可信硬件事实、停驻/唤醒来源和驱动/管理者消散后的执行根。固定平台规范须证明停止或隔离何时成立；无此证据时保留隔离资源，不以超时或维护批次完成伪造退款/复用。管理者与驱动的业务协议不进入通用 UnitOfWork，内核执行机制也不代替设备匹配与恢复政策。

各层都回看整体场景，发现冲突就更新前层结论。下面是设计推进顺序，不是可逐项提前交付的代码阶段。

| 层次 | 要闭合的内容 | 产物与退出条件 | 当前状态 |
|---|---|---|---|
| D0 系统目标与边界 | 设备体系服务哪些系统能力，哪些概念由现有领域拥有 | 目标/非目标、系统上下文、模块责任表，区分知识/进程/状态三种边界 | 已形成首稿，待 D6 整体验证 |
| D1 对象、关系与唯一状态 | 身份与描述、平台/设备/绑定/会话、拓扑/供应/隔离关系、管理域 | 领域词典、身份作用域、对象关系图和权威状态表；每个事实唯一 owner | 已补组织与 owner 表；实例及关系约束待细化 |
| D2 authority、付款与故障域 | 谁能登记、接管、转授、回收、复位；谁付费；谁能替失效 owner 收束 | 初始与运行期 authority 图、派生矩阵、预算来源、管理者死亡责任链 | 待设计；与资源层相互校正 |
| D3 跨模块协议与事务 | 登记/移除、匹配、占用/租约、驱动 Ready/停止、功能发布、供应协商 | 每种操作的前置、输入能力、提交点、返回 owner、取消/重复/迟到/超时规则；状态机及端到端时序 | 概念状态机已有，协议未闭合 |
| D4 底层机制与数据交接 | MMIO/IRQ/DMA、平台 region/reusable、等待、buffer 使用权、缓存与翻译同步 | 内核与用户态的明确职责，硬件完成证据，锁序/跨 hart/有界性，类型与接口草案 | 待设计；细节以固定硬件规范为证 |
| D5 运行装配与能力配置 | 进程划分、模块到 crate/服务的映射、启动授权、监督与关机、静态/动态配置 | 运行部署图、启动和停止依赖图、首批平台与能力表；配置不支持的能力明确拒绝 | 待设计，不预设串口优先 |

D1—D4 允许互相反馈。例如不能先冻结租约释放接口，再把 DMA 的同步条件当成后加细节。D5 的平台落点也可以推翻前层不成立的假设。总体设计阶段无需完成所有未来硬件的寄存器实现，但必须明确各能力要求什么平台事实、无法满足时如何降级或拒绝。

## 全局场景矩阵

用场景检查设计，不在本阶段增加测试程序或临时消费者。它们用于发现结构差异，不要求首批实现全部场景。

| 场景 | 检查的组合边界 |
|---|---|
| 静态 MMIO + IRQ 设备、固件原先占用 | 描述与 authority 关联、交接、固定绑定、初始化失败、IRQ 停止和复位 |
| 一个 SPI/I²C 控制器上的多个子设备 | 父子域、总线 session、请求仲裁、父故障级联、子驱动无 raw MMIO |
| 依赖时钟/引脚/复位的复合功能 | 供应共享约束、多来源组合、部分准备失败、复位影响集合 |
| 动态插入、移除、同位置重新出现 | 实例与绑定代次、发现/订阅、在途操作、迟到完成与物理消失 |
| DMA 设备的共享缓冲、驱动崩溃 | 请求完成与 backing 回收分离、有/无 IOMMU、缓存和翻译同步、隔离保活 |
| 两个功能共享不可分配资源或复位域 | 冲突粒度、授权不越界、独立会话与共同故障的关系 |
| 设备管理服务死亡、驱动仍存活 | 上级控制 authority、封闭准入、回收执行者与保守重建 |
| 启动依赖未满足、目录服务不可用 | 必选/可选装配、直接 grant、失败重试、不形成发现环 |
| 系统停止时有 I/O、租借和准备在途 | 新工作封闭、未提交回滚、已提交责任、超时升级、最终复位条件 |
| 业务饱和且恢复路径同时触发 | 公平调度、资源预备、管理入口、IRQ 风暴与长期隔离的成本 |

## 进入施工后的依赖次序

下面只是由目标结构推导的施工骨架，D6 后才能据实际接口、平台和范围冻结。每个切面迁移它影响的接口、owner、消费者和释放路径；编辑顺序不意味着中间状态可以交付。

1. **公共契约与事实来源**：把已经设计闭合的设备/驱动/供应协议落入所属模块，完成共享纯逻辑、平台事实与资源来源的接线。`os/dtb` 的解析复用/迁移需按真实消费者判断，不复制一套用户态解析模型。
2. **特权资源与安全 owner**：按依赖接通平台 region、MMIO/IRQ/DMA 对象、同步/退休、shared ABI 和 libkernel。等待、内存、内核预算的必要前置在各自计划完成，不临时绕过。
3. **用户态管理与驱动运行**：设备登记/占用机制、驱动生命周期、供应/总线协议及绑定组合按已定契约落地；组合复用进程、执行、预算和注册，不造第二套运行体。
4. **系统装配与正式消费者**：接通目标配置、平台驱动、实际功能客户端、发现和管理出口；静态或动态能力以 D5 选择为准。
5. **整体故障与收束验收**：验证正常、取消、超时、驱动/管理者死亡、移除及系统停止，并检查旧路径删除、预算返还和隔离保持。

可独立工作的模块可并行编写；测试从独立契约的最小可观察边界开始。正式系统交付仍要求选定能力的完整消费者与收束链。设计不以这份顺序强制提前建设所有未来协议，也不允许为通过中间编译补建临时机制。

## 施工准入条件

- 每个公共概念、状态和协议有唯一领域 owner，依赖图和进程授权图分别成立。
- 当前范围的请求、取消、期限、失败、退出、重试和回收均有操作 owner、提交点、结果及观察协议。
- 资源来源、控制/使用派生、付款、在途保活和退款有闭合账本；硬件安全证据明确，失败保持隔离。
- 首批平台有固定规范，布局、MMIO 属性、中断、DMA、复位/供电事实和不支持能力均有依据。
- 实际模块路径、公共类型与 ABI/wire 草案足够具体，施工者不需临时决定架构性问题；具体数据结构与性能布局仍可在契约内决定。
- 场景矩阵完成设计走查；跨专题前置有唯一 owner、顺序和完成门，选定能力没有未决正确性前提。
- 实施记录列清切面、范围、旧路径删除与验收门。当前设计授权不自动授权后续代码施工。
