# QEMU virt 驱动与外围设备：现状、成熟度差距与补完方向

> **仅供用户查阅，不是 Agent 施工入口或工作记录。** 本文是固定版本的能力与差距快照，不自动随代码更新，不创建任务、不安排优先级，也不替代所属计划中的设计、债务和验收记录。需要实施时，以届时的代码和现行计划为准。
>
> 快照基线：`e02b14108df1955b379fc242ae60926c96f7bd59`；整理日期：2026-10-28。基线是编写前的 HEAD，不包含本文。现状范围为项目当前配置的 QEMU `virt`；未来方向用于说明能力差距，不表示已经支持 QEMU 的其他设备或真实硬件。

## 当前做到什么程度

**目前是围绕首批验收路线构建的真实、受限驱动实现，尚不是成熟的通用驱动栈。** PCI、xHCI、USB boot keyboard 确实操作硬件寄存器、IRQ、DMA 和 USB 传输；设备登记、授权、按需启动、热插与停止也已经接通。实际装配和功能消费者仍主要服务于验收，不能把这条路线通过理解为系统已经具备日常输入、存储、网络和设备运维能力。

需要分开看三个方面：

- **共同机制已有实质基础**：设备与驱动管理分工、逐轮绑定、受限资源供应、观察、父子清理和 DMA 安全保留已经实现，并有相应验证。
- **具体驱动覆盖很窄**：当前重点是指定 QEMU 配置下的 PCI → xHCI → 直连 boot keyboard，USB 的枚举和传输表达还直接围绕键盘组织。
- **系统使用形态仍在建设**：驱动管理者已有持续监督，但静态常驻服务基座仅完成设计，代码仍是验收部署；真实应用入口和更广设备能力需要继续接通。

设备树中有节点、QEMU 可以模拟设备、系统能够枚举、应用能够使用，以及能够长期稳定使用，是不同的状态。下文分别说明，不以库名、类型名或已有测试数量推算完成百分比。

## 从设备到应用，各层怎样工作

| 层次 | 当前职责 | 与成熟度判断的关系 |
|---|---|---|
| 内核资源机制 | 提供受授权的 MMIO、IRQ、DMA，处理分步派生、撤销和退休 | 已有资源机制不等于支持所有平台；当前 DMA 明确依赖受信、coherent、无 IOMMU 的平台合同 |
| `srv_init` | 委托控制根、映像与预算，启动和监督设备/驱动管理者 | 已有真实监督；常驻部署、应用交付与后续恢复须按服务装配计划继续建设 |
| `srv_device` | 保存设备身份、父子关系、存在性、占用/绑定及功能入口 | 不认识驱动程序，不替硬件供应者证明安全 |
| `srv_driver` | 发现设备、选择实现、启动/复用进程、激活和发布功能 | 当前声明来自 boot 映像集，匹配是静态 identity 精确匹配加显式优先级 |
| PCI / xHCI 驱动 | 消费上游资源，操作实际硬件，登记并供应下游设备 | 是当前最需要继续扩大协议与平台覆盖的部分 |
| HID 驱动与客户端 | HID 使用限定 USB 会话，客户端直接读取 HID 功能 | 已接通 boot keyboard 状态；尚非通用 HID 或完整输入子系统 |

典型链路：`平台 PCI host → drv_pci_generic → xHCI function → drv_usb_xhci → USB 键盘接口 → drv_usb_hid → 功能客户端`。管理服务负责接管与功能取得，按键数据不经管理者逐次转发。

一个可接管设备最多有一个未释放的 Binding，每次接管有独立 epoch。Binding 的 `ResourcesReady` 表示资源备齐，驱动的 `Ready` 才表示功能可受理。驱动进程与 Binding 不是一对一：当前 PCI、xHCI 分别隔离，HID 可在同一进程承载两个 Binding，各自持有独立会话和状态。参见[装配声明](../user/services/srv_init/src/driver.rs)、[匹配实现](../user/libraries/libdriver/src/boot.rs)和[设备实现](../notes/impls/device.md)。

## 分层成熟度判断

下表是基于当前范围的定性判断，不是对未来工期的估算，也不是完整架构审计结论。

| 方面 | 当前已经成立的能力 | 距离更成熟的使用还差什么 |
|---|---|---|
| 设备管理与授权 | 登记、发现、独占绑定、资源供应、功能取得、原轮观察和停止已接通 | 通过更多真实总线、设备类型和供应关系检验共同模型；不能从键盘路线推导所有组合均已覆盖 |
| PCI | 当前 bus 0 路线、memory BAR、INTx 与 xHCI 子供应 | 更广 function 支持、桥与多层拓扑、相应资源分配和中断方案；具体范围随目标设备确定 |
| xHCI / USB | 真实控制器初始化、DMA 环、直连设备枚举、键盘传输、拔出和资源收尾 | 通用设备/配置/接口/端点表达、可扩展传输协议、hub、多接口及更多硬件适配 |
| HID / 输入 | boot keyboard 八字节报告、状态快照与变化观察 | 通用报告解析、输出报告、更多输入类别，以及应用需要的输入事件与使用政策 |
| 可靠性与故障 | 首批范围内已有正常停止、部分故障和资源竞争证据；无法证明 DMA 静止时保留责任 | 条件性精确窗口仍有覆盖缺口；广泛兼容、长期运行、性能与恢复能力尚不能据此宣告成熟 |
| 部署与运维 | boot 声明/映像、按需启动、有限候选尝试、进程监督 | 常驻服务与真实应用接入；需要时再建设驱动仓库、更新、认证及安全恢复 |

**当前在指定 QEMU 路线上已经实现功能并取得验收证据；离“可长期使用的通用 USB 和外围设备体系”仍有多块独立能力要建设。** 不能把后者理解成再添几个设备 ID 或驱动文件即可完成。另一方面，成熟也不要求实现所有 USB 类别和全部 PCI 特性；应先确定承诺支持的设备与平台集合，再证明该集合的功能、失败和长期运行合同。

## 当前配置与已接通能力

项目的 [`Justfile`](../Justfile) 为 virt 配置 1 GiB RAM，使用 `-nic none`，并显式添加 `qemu-xhci` PCI 控制器；控制器使用 INTx，关闭 MSI/MSI-X。默认命令没有预先附加键盘，设备验收工具通过 QMP 在运行期插拔 `usb-kbd`。

| 能力 | 当前状态与用户可见边界 | 主要实现 |
|---|---|---|
| PCI host | 扫描 bus 0，当前子供应面只接一个 xHCI；拒绝未支持的桥拓扑，不是任意 PCI 设备的完整支持 | [`drv_pci_generic`](../user/drivers/drv_pci_generic/) |
| xHCI USB 主控 | 只接纳 QEMU `qemu-xhci` 的 vendor/device `1b36:000d`；使用 MMIO、IRQ 和 DMA 管理直连端口、枚举与传输；连接容量上限为 2，实际 slot 数还受硬件能力约束 | [`drv_usb_xhci`](../user/drivers/drv_usb_xhci/)、[`libusb::xhci`](../user/libraries/libusb/src/xhci.rs) |
| USB boot 键盘 | 接口出现后匹配并启动或复用 HID 驱动；实际验收包含输入、热插及双连接/多 Binding 进程复用 | [`drv_usb_hid`](../user/drivers/drv_usb_hid/)、[`test_device`](../user/tests/test_device/) |
| 键盘状态语义 | 提供当前按键集合、有效/不确定状态和报告序号；提示可合并，不保证每个短暂按键边沿无损。ErrorRollOver 不伪装成全部释放 | [`libhid`](../user/libraries/libhid/)、[键盘合同](todo-2026-09-device-system-design.md#usb-transport-与键盘功能) |
| 外部中断 | 内核 PLIC 将获授的 PCI INTx 连接到用户态等待、领取和确认 | [PLIC 与 IRQ 实现](../notes/impls/device.md#plic-平台与中断机会) |
| 控制台日志 | 内核通过 SBI debug console / legacy console 输出；尚不能作为用户态串口功能服务使用 | [`console.rs`](../os/kernel/src/console.rs)、[`sbi.rs`](../os/kernel/src/sbi.rs) |

## USB 为什么还不能称为通用栈

### 主控适配明确限定 QEMU 型号

[`Controller::adopt`](../user/libraries/libusb/src/xhci.rs) 明确检查 PCI vendor/device 为 `1b36:000d`，其他型号返回 Unsupported；还拒绝需要 scratchpad buffer 的控制器配置。代码注释明确提醒，当前依赖的 QEMU detach 行为不能直接外推真实硬件。因此现状比“只在 QEMU 测过”更窄：其他 xHCI 型号目前在代码入口就被拒绝。移植到真实主控需要重新核定适配与停止证据，不能只删除型号检查。

### 枚举与接口表示仍围绕键盘

[`libusb::xhci::device`](../user/libraries/libusb/src/xhci/device.rs) 的 Device/Interface 记录直接持有 `Keyboard`，配置读取后调用 `keyboard_configuration`，再依据所选键盘端点配置硬件。[配置解析](../user/libraries/libusb/src/descriptor.rs) 寻找 alternate setting 0、class/subclass/protocol 为 `03/01/01` 的 boot keyboard Interrupt IN；遇到第二个匹配端点返回 Unsupported。

这已经能完成当前目标，但没有交付面向任意 USB 类驱动的完整枚举与接口发布能力。即使解析器能跳过其他描述符，也不能据此宣称支持复合设备的多个接口、配置选择或 alternate setting 切换。现有总线层中的键盘知识是后续通用化必须重新审视的边界；届时如何拆分由所属设计确定，本文不提前规定新的服务或模块划分。

### 对外传输接口只有两种业务

当前 [`libusb::protocol::Transfer`](../user/libraries/libusb/src/protocol.rs) 仅有：

- `BootProtocol`：为本接口设置 boot protocol。
- `InterruptIn`：读取键盘报告，完成结果固定最多 8 字节。

内部枚举会执行设备/配置描述符等控制请求，但这些内部能力不等于已向类驱动开放通用控制传输 API。当前没有交付任意控制请求、通用 Interrupt IN/OUT、Bulk 或 Isochronous 的类驱动接口。USB 存储、打印、音频等不能仅新增匹配声明就使用现有会话。

每个接口会话最多一份未确认请求，以 seq 保持重复提交、结果读取和取消的一致性。完成通知只提示读取原结果，无输入时不周期查询；硬件环和 DMA 缓冲仍由 xHCI 持有。这些责任可以作为后续设计的现状依据，但扩大吞吐、载荷和并发时，需要重新闭合容量、流控、完成、取消与内存寿命。

### 拓扑、速度和输入功能的范围有限

外置 hub、复合设备多接口、通用 HID、键盘 LED 输出均未交付；双连接验证的是两个直接连接和独立 Binding，不证明复合设备支持。当前枚举的速度处理只接受 low/full/high speed，不能因使用 xHCI 就推导已有 USB 3 SuperSpeed 设备支持。

HID 当前交付按键状态，不拥有完整的应用输入策略。鼠标、触摸等类别，通用 report descriptor 解析，以及需要保留每个事件的输入队列都要继续建设。若应用需要键盘布局、文本输入、按键重复、焦点或多设备合并，还须确定其上层服务归属，不能将这些能力归给现有八字节报告解析。

### 安全退出已有基础，恢复仍有限

正常停止时，相关驱动要停止接纳、收束在途传输，完成实际端点/slot 清理以及 DMA、IRQ、MMIO 退休，之后才能释放绑定。USB 接口供应者 xHCI 能在 HID 死亡后继续承担硬件收尾；直接访问物理资源的 PCI/xHCI 则需要真实停止证据。

当前不自动重启失效的设备登记服务或 DMA 主控。主控死亡且没有安全证据时，保留 DMA pin 与费用并升级系统故障，进程 DONE 或关闭句柄不能替代硬件静止。因此，“能安全保留危险资源”已经有实现，但“故障后恢复设备并让应用继续工作”尚未成为完整能力。参见[设备故障合同](todo-2026-09-device-system-design.md#正常停止与无配合故障)与[管理者监督](../notes/impls/device.md#init-的管理者监督)。

## 平台可见，但未接通的用户功能

以下依据项目的 [`virt/device.dts`](../os/platforms/qemu/virt/device.dts) 和当前设备计划。“未接通”指没有确认作为面向应用的完整设备功能交付，并非 QEMU 无法模拟。

| 设备 / 设施 | 当前认识 | 补完时需要形成的能力 |
|---|---|---|
| NS16550A 串口 | DTB 有串口，现有内核日志走 SBI | 应用串口所需授权、驱动与功能协议，覆盖输入、输出、退出和故障 |
| Goldfish RTC | DTB 有节点，当前路线未交付应用 RTC 功能 | 按时间服务需求确定读取、设置与授权语义，再接入消费者 |
| VirtIO-MMIO | DTB 有 transport 槽位，槽位不代表已经附加块设备或网卡 | 选定实际 transport/设备配置，接通资源、VirtIO 协议、类别驱动和消费者 |
| 网络 | 默认命令关闭网卡，当前路线未提供联网能力 | 网卡驱动之外还需要网络服务、协议栈及真实应用数据路径 |
| 外部块存储 | 当前 PCI/USB 路线未提供应用可用的块设备链 | 块驱动、请求与缓存/持久化语义、文件系统接入；已有文件服务不等于已有磁盘链路 |
| PLIC、CPU 本地中断、计时设施 | 内核或平台基础设施 | 随平台扩展，不作为普通应用可直接取得的外围设备 |
| QEMU test/syscon | DTB 有平台控制节点，reset 有现有平台/SBI 路径 | 不把节点存在当成已发布通用用户设备 |

## 以后需要补什么，怎样才算补到位

以下为用户查阅的能力缺口与可观察目标，不是新的施工合同或排期。已有延期事项仍由[设备计划](todo-2026-09-device-system-design.md#延期能力的唯一登记)拥有；未立案方向在实际需要时确定范围、设计和验证。

| 方向 | 需要补齐的内容 | 可以据以判断进展的结果 |
|---|---|---|
| 常驻部署与应用接入 | 从验收装配进入正式常驻基座，交付受限功能入口，接上真实应用与正常关机 | 系统持续提供服务，运行期插拔后应用能发现、使用和处理断开；结束验收不再是唯一使用形态。已有[服务装配计划](todo-2026-10-07-service-assembly.md)承接 |
| USB 通用设备模型 | 重新审视运输层中的键盘依赖，补设备、配置、接口、端点的完整表达与授权 | 新的非键盘类驱动可以取得自己的受限接口，而不要求每个新类别都在主控状态机中增加专用路径 |
| USB 通用传输 | 按实际消费者补控制、Interrupt IN/OUT、Bulk；音视频需要时补 Isochronous；形成相应缓冲、队列和取消合同 | 除键盘报告外，真实业务数据能完成传输；并发、队列满、超时、拔出和停止时仍能追踪每个已接请求 |
| USB 拓扑与配置 | 外置 hub、复合设备多接口、所需配置/alternate setting、目标速度档位 | 同一父设备下接口可按合同独立工作/停止，父级故障正确影响后代；目标 hub 和速度档位有实际验证 |
| HID 与输入服务 | 通用报告解析、输出报告、所需鼠标/触摸等设备，以及应用输入服务 | 对目标设备和应用形成完整输入行为；需要逐事件交付时，有容量、溢出与重同步语义，不以状态通知冒充无损流 |
| 新类别驱动与系统功能 | USB 存储/打印、VirtIO 块设备/网卡等按产品需求选择；接通对应上层服务 | 真实应用完成读写文件、收发网络数据或打印等操作；枚举成功、提交一次传输不单独算功能完成 |
| PCI 与平台扩展 | 更广 PCI function、桥与资源布局；按目标需要补 MSI/MSI-X、共享 IRQ、PCI 热插和更多平台资源 | 承诺的多设备/拓扑能并存、退出和处理故障，不再依赖当前一个 xHCI 的配置 |
| DMA 与硬件信任 | 目标需要时补 IOMMU、非一致 DMA、缓存/翻译同步；平台保留区按独立计划处理 | 隔离和退休保证与真实平台相符；当前 TrustedPhysical 能力不能作为允许不可信 DMA 的依据 |
| 故障恢复与运维 | 在硬件安全可证明的条件下设计复位/重建、应用重连；镜像外驱动需要仓库、安装更新和来源认证 | 故障后恢复的是新身份与有效会话，不复活旧能力、不复用仍可能被 DMA 访问的页；更新与选择有明确政策 |
| 兼容、性能和长期运行 | 确定目标设备矩阵、真实硬件范围、负载与资源预算，取得相应证据 | 给出实际吞吐/延迟/CPU 占用及长时间、多设备、反复插拔下的结果；区分已测设备、未测设备和明确不支持项 |

不必把上述方向全部实现才交付某个有限目标，也不宜一次性预建全部机制。可以按三种使用目标理解距离：

1. **当前 QEMU 键盘可长期供应用使用**：已有主要硬件链，仍需常驻装配、真实应用接入，以及该使用合同需要的可靠性证据；不必先实现 USB 音视频或驱动在线更新。
2. **可扩展的通用 USB 子系统**：需要重新闭合设备/接口模型和传输表达，并用不同类别、拓扑验证，而不只增加 boot keyboard 变体。
3. **面向选定真实平台的成熟外围设备支持**：在前述基础上补目标平台、中断/DMA、兼容性、性能、长期运行和所需运维能力。能力集合和硬件范围未确定前，不能给出可靠百分比或工期。

## 验证证据与阅读边界

设备计划已记录首批真实 PCI/USB/HID、热插与多 Binding 复用、真实 IRQ 唤醒、部分驱动死亡、回复缺失、MMIO/IRQ/DMA 退休及竞争场景的证据。这些足以说明当前实现有真实责任链，不能外推为全部设备兼容或所有故障窗口已验证。

当前条件性覆盖缺口包含准备末尾封来源、发现 RPC 在途停止、指定 USB 配置间隙拔出、CPU Unmap 分配失败，以及进程装载取消交错等。它们是覆盖边界，不自动表示仍有已证实的代码缺陷；也不因本参考清单更新而重新安排实验。具体触发、原证据和补证标准继续由[修复后接续](todo-2026-09-device-system-design.md#整体审查修复后的接续2026-10-28)拥有。未归因历史异常按 [KNOWN_ISSUES](../KNOWN_ISSUES.md) 的观察规则处理。

本快照通过源码、当前实现说明与计划交叉核对，未重新运行编译或 QEMU；上文运行结论均引用已有记录。没有对全部驱动做新一轮完整架构审查，也没有完成真实硬件兼容性或性能评测。
