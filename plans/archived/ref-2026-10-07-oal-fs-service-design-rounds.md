## 目标与边界

重新确定路径与 namespace、节点身份、目录/属性/流、授权与能力导出、服务发布发现及 provider 的边界。按独立需求决定保留、合并或替换现有概念，使接口承载完整领域责任，减少消费者必须理解的内部状态和机械清理。目标不受现有 ABI、FAL 结构或测试布局的兼容约束。

### 外部参照及适用边界

- [Fuchsia fuchsia.io](https://fuchsia.dev/reference/fidl/fuchsia.io)：`Directory.ReadDirents` 的 dirent 只有 inode、类型与名字；`Directory.Open` 建立连接，`Rights` 属于连接并限制可授予新连接的操作；`Directory.Unlink` 明确仍打开的对象可在引用关闭前存活。采用的参照是观察/取得连接/名称关系分离，不照搬其 flags、组件框架或 wire。
- [Genode Foundations 23.05：Services and sessions](https://genode.org/documentation/genode-foundations/23.05/architecture/Recursive_system_structure.html)：父节点可以把 session 请求路由给另一子组件，服务创建 session，能力沿请求链返回；之后客户端直接与服务交互，中间组件不在实际使用的关键路径。支持把发现/装配和业务 session 分开；不据此推断其文件 unlink 语义或本项目应采用同样付款机制。
- [Plan 9 remove(5)](https://9p.io/magic/man2html/5/remove)：同一文件的其他 fid 在 remove 后是否仍可访问由实现决定，Plan 9 文件服务器与 U9fs 行为不同。这是反例：统一 namespace 并不能替我们决定已打开对象的生命周期，必须在本案明确约定。

上述官方资料用于比较机制边界，不是本项目协议的固定版本规范；尚未核实的第三方细节不纳入目标契约。

## 第二轮设计：通用 FAL 与上层领域

用户指出第一轮仍以服务发现塑造 FAL，要求同时考虑设备描述、驱动发现，并区分通用机制与上层组合；随后明确 `/System/Services/` 等是由 FAL 组装的 `/System/` 视图，四类需求须同时推导基础能力。**先共同设计普通文件、服务发现、设备描述和驱动声明在 FAL 上的表达契约，再确定通用基础和各领域接口。** 领域拥有各自内容与协议；FAL 拥有通用命名空间组装及访问机制。以下分层是当前设计基线，具体接口仍须经 G1 闭合。

| 所属层 | 拥有的语义 | 不代替的责任 |
|---|---|---|
| 内核对象与 capability 运输 | 对象身份、内核 rights、复制/转移及运输约束 | 解释服务、设备或驱动的业务权限 |
| 通用 FAL/文件访问 | 目录与名字绑定、节点/属性/内容访问、观察、自身访问权、通用对象引用及跨 provider 命名 | 服务 Ready/Drain、设备资源占用、驱动匹配或它们的业务授权 |
| 服务领域 | 服务描述 schema、实例与发布状态、名字发布/替换权限、发现与会话取得契约 | 通过 FAL 位集表达任意服务协议的权限；成为所有领域的注册状态机 |
| 设备领域 | 设备身份/描述/拓扑的权威状态、登记来源、占用/租约、资源授权及隔离回收 | 从可读设备属性推导 MMIO/IRQ/DMA 使用权 |
| 驱动与装配领域 | 驱动声明、匹配规则、映像与执行授权、绑定选择及启动/监督 | 从目录可见性推导允许启动或绑定；让 FAL 选择驱动 |

### 通用机制的边界判据

- **命名是共同访问方式，领域语义不依附路径。** 服务记录、设备描述和驱动声明都可通过 FAL 提供可枚举、可观察的视图；持有领域入口的客户端也可直接使用对应协议。启动与恢复不能为取得已有能力强制绕经发现目录。不要求这几个领域复用 `Starting/Ready/Draining/Terminal` 生命周期。
- **FAL 保有自己的授权，但不生产其他领域的权限。** 遍历/读写目录与数据、取得命名引用属于 FAL；发布某服务名、取得某设备租约、允许某映像驱动某设备分别属于领域及装配 owner。访问一个已获准公开的能力入口可能合法交付该能力，但交付范围已由签发者和发布者确定，FAL 不能根据描述自行 mint 更强业务权限。现状也不是所有授权都在 FAL：[libservice AuthorityTable](../../user/libraries/libservice/src/authority.rs) 已独立管理名字发布 scope；问题是 [service protocol](../../user/libraries/libservice/src/protocol.rs) 与 ExportPolicy/FalRights、Record、目录导出路径耦合。
- **允许通用的能力承载，拒绝领域特制的授权解释。** 搬运已经签发且允许转授的不透明 capability 可以是通用能力；它不等于读一个字段就代替设备分配租约、替服务建立会话。不能把内核 transport rights 收窄当作 FAL 或其他领域的业务权限衰减，也不能把原始整数/路径字符串当作有权限证明的入口。第三轮选定节点的 Reference 能力及显式 Acquire；第一轮“一律删除能力表示”的预判已撤回，现有混合策略类型仍需拆解。
- **上层拥有 schema 和投影。** FAL 核心不枚举 Service/Device/Driver 特例、不解析这些领域的属性名、协议号和状态；上层通过完整的通用 provider 契约提供视图。领域权威状态保持唯一，投影不成为第二份可独立修改的真值。是否保存数据、按需生成视图或缓存由完整一致性契约决定；同进程组合不改变知识归属。
- **引用与观察的通用语义不能偷偷扩大。** 目录绑定身份及快照/变化一致性可以通用，服务实例、设备重插代次、驱动包版本分别由领域解释。投影消失不证明服务会话已撤销或硬件已停止；管理者消散也不要求设备描述消失，上级可以保留故障视图。capability 有副本不等于允许重复分配同一排他资源。
- **可复用性需要独立反例。** 加入设备描述或驱动发现，原则上只应新增其领域 schema、协议、投影实现和装配；若必须在 FAL 核心新增它们的操作码、授权位、类型分支或回调语义，就需要重新检查边界。也不能用一个通用 Control/Invoke 加领域操作号，或藏在回调里的分支，掩盖 FAL 核心对领域的反向依赖。明确的 FAL 自身扩展仍可依据独立共同需求重新论证。

第一轮将观察与取得分开的思路保留为使用契约：客户端能够只观察而不申请领域资源。它不能单独决定 FAL 的值类型，也不意味着所有领域都必须实现统一 Connect。以下共同需求先于服务注册表共享授权、工厂和转发等实现选择。

### 用户确认的统一视图与共同需求

`/System/Services/` 是服务发现视图；设备、驱动及未来系统领域在 `/System/` 下提供各自视图。`/System/Devices/`、`/System/Drivers/` 在本轮仅作具体子树名称的示意。普通文件通过同一 FAL 体系访问，其目录不要求放进 `/System/`。`/System/` 是命名空间布局，不是 FAL 核心硬编码识别的业务前缀。

“由 FAL 组装”指 FAL 提供跨 provider 子树接入、路径解析、引用及访问边界等完整组合契约，装配者依据系统布局和授权使用它。各领域提供视图和协议，FAL 不凭路径识别领域，更不要求一个全局文件服务拥有所有领域状态。真实对象关系可以是图，目录树只是访问视图；描述关联与可行使权限的能力引用要明确区分。

四类需求是共同设计输入，设备和驱动不再只是服务方案完成后的附加反例。本案须同时闭合它们在 FAL 上的表达与组合契约；设备资源模型、硬件操作和完整驱动运行仍由设备分案实施，不把“共同设计需求”误记成那些能力已完成。

| 需求面 | 必须能经 FAL 表达的部分 | 领域拥有的内容及操作 |
|---|---|---|
| 普通文件 | 目录/名字、稳定对象访问、内容与基础属性、创建/删除/改名的支持及失败语义 | 具体存储后端、持久性和专属操作的承诺；不会因统一节点而要求所有视图支持文件写入 |
| 服务发现 | `/System/Services/` 中的枚举、描述、可取得的协议入口及绑定变化；描述和所取得入口必须对应同一绑定 | 服务 schema、发布权限、实例与就绪/排空、会话准入及业务协议 |
| 设备描述 | 设备身份、属性、关系及可观察状态的视图；查得对象与后续领域请求能够核对同一实例 | 描述可信来源、物理拓扑、占用/租约、资源授权和硬件收束 |
| 驱动声明 | 候选声明的枚举与读取、声明身份/修订以及映像或协议入口的关联表达 | 匹配规则含义、候选优先级、可信映像、选择/绑定/启动授权 |

由这些需求推导的基础候选按语义归组，不预先等同于六种节点、六条 syscall 或六个模块：

1. **命名与组合**：目录、名字绑定、子树接入和路径解析；不同 provider 的视图能够组合，访问根与授予范围明确。
2. **对象与引用**：节点身份与名字绑定分离，取得对象后不因同名替换而误指；内容中的描述性关联、FAL 对象访问权和不透明协议入口不能混成可互换整数。
3. **数据访问**：能够表达普通内容和结构化描述，明确部分读取、更新和不支持某操作的语义。第三轮选定 Content 字节+格式及版本条件读取，领域保有结构化编码；流运输的完整完成语义在 G2 闭合。
4. **访问能力与转授**：FAL 自身操作权和引用交付的通用约束；领域 capability 的业务权限仍由签发者决定，声明可读不等于资源可用。
5. **一致性与变化观察**：枚举/读取与变化通知有可说明的一致性关系，能发现替换并避免把不同对象或不同快照的结果拼接；领域的状态值和生命周期不进入通用状态机。
6. **操作及资源责任**：每种通用操作有明确提交结果、取消/失败、持有和释放语义，跨 provider 组合也能保持；精确 owner 和预算由 G1/G2 闭合，不让未来领域各自补一套通用清理协议。

“基础”以语义独立、可组合、责任闭合和未来上层可扩展为标准，不以最少操作数限制设计。某种需要不必由四类消费者全部使用才能成为基础能力，但必须有领域无关的契约与独立需求依据。新的 schema、provider 或领域协议通常可以复用基础；确有新的共同语义时允许演进 FAL，并重新核对所有消费者。

### 在上述分层内继续成立的约束

1. **统一名字访问，分开观察与领域能力申请。** 普通文件、目录、服务视图、设备描述和驱动声明可以处于同一 namespace；观察操作不隐式创建服务会话、申请设备租约或触发驱动绑定。FAL 通用内容和引用的表达由 G1 决定，不能先为了服务连接发明节点类型。描述可携带由上层解释的 schema/协议信息；Open/Connect 在本文是语义名称，不表示所有领域共用一个 FAL 操作码。
2. **取得能力的结果自身完整。** 服务连接在一次成功结果里返回实际选中的发布身份、协议信息和能力，消费者不必先 Describe。先观察再连接的调用者可以要求匹配既见的发布身份；替换后返回冲突，不能静默转到新实例。不带期望身份则选择本次实际绑定。纯数据快照与能力在同一个动作结果里组合仍然合法；消息/RPC 传 handle 的能力不受限制。
3. **路径位置与稳定访问权分开。** 名字是目录中的绑定；对象身份在 rename 后保持；打开后持有稳定对象访问权。同名重建不改变旧访问权指向的对象。Create/Delete/Move 修改父目录名字关系，数据读写作用于已绑定对象；一次性按名动作可以在 provider 的一次执行中解析并操作，不要求每次 stat 或每个路径分量都 mint sender。
4. **身份、绑定变化和数据版本各司其职。** provider 内 NodeId 不当作全局身份；跨 provider 身份必须带其身份域。对象身份用于防止同名替代，名称绑定的代次用于观察替换，数据版本用于条件修改。不能把三者压成一个 generation，导致普通内容修改无故使按身份 Open 失败。最终字段和溢出策略由 G1 确定。
5. **授权由拥有该权限语义的 provider 决定。** namespace 可达性、描述读取、能力获取分别授权；得到名字不等于得到调用权。FAL 权限衰减仍由真实 FAL provider 检查，内核 sender rights 裁剪不能替代它。服务的会话参数、业务权限和准入由服务拥有；registry 不解释任意协议的权限位。付款身份与授权身份分开，不凭可伪造请求字段决定账户。
6. **撤发布阻止新的按名获取，已有访问权由其 provider 管理。** 名称 owner 的发布/替换权限与服务实例分离；旧实例清理必须条件匹配自己的绑定，不能删除替代者。已建立会话可继续、排空或被 provider 撤销，按该领域契约执行；Watch 只通知变化，不自动重连、迁移会话或证明旧能力失效。FAL GrantTable 已有按 context 拒绝后续请求的机制，不先立一个内核通用撤销树前置。
7. **删除领域耦合，保留真实完成责任。** 通用值/引用不应为服务 Record 特判 Directory 再代签授权；FAL 自身目录派生仍由其 provider 负责。纯数据 Record、不透明能力引用和一次性移交分别按独立契约论证，不能因现存 probe 或服务消费者少而先行删除。流 EOF、业务 Finish、取消、Close、Unmap 仍表示不同事实；Copy 的已提交部分和结果未知必须可观察，不能靠默认重试或 Drop 伪造回滚。

### 前两轮排除项与候选的收敛

- 只把 ReadTask/DelegateTask 搬进另一个通用 task，仍让值模型按具体领域协议代签授权：只移动代码，没有解除通用表示与领域授权生产的耦合。
- 为统一访问而抹去描述结构，或强迫一字段一文件：第三轮采用 Content 字节运输，但结构化 schema 完整留在上层，同一描述仍可一次性表达。
- 所有名字都立刻 mint 独立对象 sender：会把枚举、观察和路径每一跳都变成资源创建；稳定访问权只在需要持有时建立。
- 发布时统一预派生一次，以后全用 duplicate：仅当发布契约允许共享授权身份、付款及寿命时成立。duplicate 共享 sender context，不能替代独立会话、逐客户端撤销、动态衰减或独立配额。此方案是固定共享授权的候选，不作为所有目录/服务的默认。
- 所有连接都经通用工厂/代理：可由 provider 在确需独立 session、准入或动态授权时承载；不能为理论扩展先建立第二套通用运行体。显式获取可能仍需下游 RPC，其 owner/取消责任真实存在；不把 ReadTask 删除等同于远端状态机全部消失。
- 立即合并 libfal/libfs/libservice，或新增万能节点管理器：先闭合语义及依赖方向，再决定模块。统一命名不要求服务 registry、内存文件后端与进程监督共享状态机。

**前两轮服务层候选的处置。** 第三轮选定 Reference 只交付已签发的可共享能力；需要独立 session 时，客户端通过该入口使用领域协议。通用 Acquire 不转发任意领域签发请求。服务层是否还有自身中介/工厂，是它的协议和装配选择，不能反向改变 FAL 表达。跨 provider 的 FAL 目录访问仍须由真正发行者收窄自身访问权；其责任不再藏在服务 Record 的属性读取中。

该路线需处理三个已核实的限制：

- `GrantTable::prepare_derive` 继承父 grant 的 account，当前每次目录 Record Read 会增加 provider 的 grant/观察占用；已有准入上限，不能仅凭占用增长宣称已证实 DoS 漏洞。改成共享授权可以减少同一发布对应的 grant 数，但独立获取者付款须另有可信资金绑定，不能在请求里随意声明账户。
- grant 持稳定 NodeRef；稳定 pin 本身可以共享。duplicate 共享 sender context，现存 Watch Query/Unsubscribe 按该 context 鉴权，因此共享者之间不再具有逐次派生带来的订阅管理隔离。G1 必须决定订阅管理权是否需要独立 capability/session，并将这个代价计入比较。
- `GrantTable::revoke` 只拒绝后续请求；正常 `provider::Grant` 在 Lifetime CLOSED 后撤 source，再 remove 表项。共享授权的最后持有者可以延长其占用，registry 撤发布关闭自己的引用不等于该占用已归还。所有尚存的发布代次/授权均须持续计费和受准入上限约束，不能按“当前名字数”提前退款。

### 贯穿场景与目标责任

下列场景检验四类共同需求的责任链；设备描述和驱动声明的表达契约须共同设计，其代码仍未接通：

- **发现并使用第二个文件服务。** init 向 B 交付受限的发布授权；B 以真实 FAL provider 身份准备可导出的入口并发布。消费者观察服务名字而不取得 FAL 权限；显式获取时选定发布实例、完成授权并取得描述与目录访问权，然后用同一访问权进行文件操作。绑定撤出后新获取失败或选择替代实例；已有访问权不会悄悄变成新实例。跨 provider 路径 `/second/...` 必须遵守相同的出口授权规则，不能交出过宽母 grant 后要求客户端自觉收窄。
- **跨 provider 文件 Copy。** 源取得稳定读访问权，目标独占创建并取得稳定写访问权；搬运和两端业务完成分别结算。取消保留已提交部分，不能误删被替换的同名目标。已投递 Create 没有结果时保持未知，不自动重试创建或按名字删除。是否让 Create 同次返回对象访问权由 G2 详细闭合。
- **设备描述与资源取得。** FAL 提供某设备的身份、属性和关系视图；消费者观察它不产生硬件资源授权。申请租约走设备领域契约；同位置重插须匹配实例，管理者故障时可以保留诊断描述，不能从节点删除推断 DMA 已停止或资源已退款。设备设计仍由[设备分案](../todo-2026-09-device-system-design.md)拥有。
- **驱动候选与绑定。** FAL 可承载驱动声明及变化视图；声明的 schema、匹配、多候选选择、可信映像和绑定授权由 driver/装配领域拥有。枚举或获取声明不能触发启动/绑定，目录条目增加也不等于它有权控制已发现的设备。

能力获取准入前不对外发布结果；准备中的节点 pin、付款、目标引用、临时派生能力由当前操作持有；交付失败沿该操作收束。成功交付后客户端持访问权，provider 持业务对象/会话和其退休责任。涉及远端签发的精确提交点、撤发布与在途获取的先后关系仍阻塞在 G1，不把“同次返回”当作跨服务全局事务。

## 第三轮设计：基础表达 v0

本轮用户授权将四类需求收敛为实际设计。以下记录第三轮形成的基本表达及当时取舍，未曾实现。第四轮指出其中 Content 混淆对象描述与文件数据，且整体实际上已上移为对象抽象；本节不能继续作为完整施工目标，需按第四轮边界重审能力集合、操作及知识落点。身份/绑定区分等结论可按各自独立理由承接。

### 1. 一个节点，三种可组合的通用能力

采用稳定节点及固定能力组合，不采用 Service/Device/Driver 等领域节点类型：

```text
Node       = NodeKey + Facets + RevisionedState
Facets     ⊆ { Directory, Content, Reference }
Directory  = Name → Binding(Target, BindingStamp)
Content    = Bytes + FormatId
Reference  = 已签发且允许交付的 capability + 运输权限上限
```

这些是语义类型，不是内存结构、wire 字段布局或新内核对象。一个节点至少提供一种能力，能力集合在该 NodeKey 的寿命内固定；改变集合须建立新节点、条件替换名字绑定。暂不可用、权限不足和不支持能力是不同结果，不能靠临时改变类型表达服务启动或设备离线。

| 能力 | 表达及接口含义 | 独立需求 |
|---|---|---|
| Directory | 具名绑定的集合，支持查找和枚举；可写目录另支持名字修改 | 普通目录、服务列表、设备拓扑视图、驱动候选集合 |
| Content | 有格式标识的字节内容，支持按范围读取；可写内容支持范围写或整体替换 | 普通文件数据及领域拥有的结构化描述 |
| Reference | 显式取得一个已签发 capability 的副本；没有安装引用时返回 Unavailable | 协议入口、已授权对象引用；动态资源申请仍走取得入口后的领域协议 |

能力可以组合：普通目录是 Directory，普通文件是 Content；服务条目可以是 Content+Reference；设备节点可以同时具有 Directory+Content+Reference。没有内容或没有可公开入口的节点不必提供相应能力。不按组合再建立七种专用 NodeKind。

一个 Reference 提供一个能力引用。需要多个独立入口时，用 Directory 下的具名子节点组合；共享领域上下文和需要原子交付的一组能力由其领域协议负责。FAL 不因多端点服务增加任意能力数组、方法分发表或业务事务接口。

### 2. 内容保留结构，FAL 不解释结构

本版选定 Content 的运输表达为字节及不透明 FormatId。普通文件可以是任意二进制；服务描述、设备关系和驱动匹配声明仍是结构化内容，其编码、版本兼容和校验由所属领域负责。FormatId 标识内容解释方式，不是 FAL 可分派的操作号或权限证明。

不强迫每个字段成为一个文件，也不把内容自动解析成 FAL 的递归 Record/Array/Handle。共同的纯数据编码可以由领域按独立需求复用，但不成为 FAL 的必需值语法。通用工具能取得名字、身份、能力集合、格式、长度和版本；理解具体字段需要相应解码知识。牺牲内建字段反射换取编码和领域演进的独立性，是本版明确取舍。

FAL 的节点固有信息只有访问所需的通用事实；设备状态、服务实例、驱动版本等在 Content 中。域内关系可以用领域身份表达，面向浏览的关系也可提供目录别名或路径链接。数据中的 ID/路径不获得授权，不能冒充 Reference 或 NodeAccess。

如果后续需求证明字段级观察、通用结构查询或字段级独立授权是不可替代的共同契约，再据该需求评估扩展。本版不通过解析未知 schema 提供这些能力，也不为了调试展示把领域规则塞进 FAL。

### 3. 身份、名字与访问权

| 概念 | 唯一含义 |
|---|---|
| NodeKey | provider 实例身份与其节点身份的组合；同一 provider 实例内不复用。标识对象，不授予访问权 |
| BindingStamp | 某目录名字绑定的一次成立；删除重建、改指或移入都会产生新 stamp，用于条件名字操作 |
| Revision | 同一节点对外表示的修订；本节点内容、公开引用或目录成员变化推进它，子节点自己的内容变化不自动推进父节点 |
| NodeAccess | provider 签发的、绑定到节点及操作范围的实际访问能力；调用者不能用 NodeKey 自行重建它 |

三种标识不混用。按对象身份 Open 不因普通内容写入失败；按名字条件删除使用 BindingStamp；要匹配描述与引用则使用 NodeKey+Revision。计数耗尽不能回绕复用；具体表示宽度与耗尽处理在 G1 wire 设计落实。持久文件标识可属于存储描述，不能让重启后的 provider 复活旧访问能力。

目录项指向节点或作为路径解析指令的链接；跨 provider 的目录目标携带受限 FAL 目录访问权。普通别名和挂接复用节点身份，不复制目标状态。路径只是通过这些绑定到达节点的一种方式，已有 NodeAccess 可直接操作对象。

Rename/Unlink 改父目录的名字关系，不改目标的能力集合或身份。要求“空目录”时，空仅指 Directory 成员为空；同节点有 Content 不使空目录判断含糊。Unlink 不递归删除目标子树，不承诺撤销已打开对象。对象退休由节点 owner 和实际持有关系决定。

符号链接保存路径表达式，由 namespace 解析器处理；它不成为领域协议入口。绝对路径相对于调用者获得的 namespace 根，`..` 不越过所授根，也不根据目标 provider 的物理父节点逃出组合视图。重定向和跨 provider 行走消耗调用者明确的工作/资源预算，耗尽返回错误，不无限追随或以任意旧常数冒充硬件上界。

### 4. 观察、内容与引用的版本契约

单节点的 Content、Reference 及其公开表示共享 Revision。provider 必须从同一权威状态生成它们；更新相互关联的描述与引用必须同点提交。一个节点拥有多个能力，本身不自动产生一致性。领域可以持有不可变表示再整体替换，或在自己的序列化状态机中提交；FAL 不另保存可独立修改的副本。

基础操作采用以下逻辑接口，名称尚不是 wire 调用号：

| 操作 | 成功结果及并发含义 |
|---|---|
| Inspect(access) / InspectChild(directory, name) | NodeKey、固定能力集合、允许操作与当前 Revision；按名查看另返回 BindingStamp，不 mint 稳定 NodeAccess、不交付 Reference |
| OpenChild(directory, name, expected_binding?, requested_access) | 选择一个绑定并取得稳定 NodeAccess；原子核对预期绑定和授权。完成后名字替换不会改指已取得对象 |
| List(directory, cursor, expected_revision?) | 有界的一页名字、BindingStamp、目标身份/固定能力摘要；不逐项 mint NodeAccess 或交付领域 capability |
| Read(content, range, expected_revision?) | 一个修订下的字节、格式与 Revision；有预期版本而不匹配则返回 Changed，不拼接不同修订 |
| Acquire(reference, expected_revision?) | 已安装引用的 capability 副本及 NodeKey、Revision；本地检查、复制及结果 owner 准备完成后提交，不调用引用所指协议 |
| Observe(access, after_revision) | 独立订阅能力；原子完成“比较版本并建立观察”，避免读后订阅的丢失窗口 |

首次 Read/List 可以选择当前修订，后续分块或分页带上该 Revision；发生变化时整体结果作废并显式返回 Changed。基础契约不保留任意历史版本，不保证在持续修改下总能获得完整快照；调用者按期限/预算决定重试，不在通用库中无限重试。确需稳定长快照的领域可以发布不可变节点修订，或通过自己的快照协议提供；不是所有文件都承担历史快照存储。

List 的修订只保证本目录的绑定集合；摘要不夹带声称同一快照的子节点大小、状态或内容版本。查看这些可变事实须 Inspect/Read 相应节点。单次 Read 的字节也必须来自它返回的那个修订，不能先比较 Revision 再无保护读取变化中的 backing；零拷贝运输须保持所交付片段不可变或有等价保活契约。

服务等需要“描述和入口相配”时，通用组合步骤是：

```text
OpenChild → 固定 NodeAccess 和 NodeKey
Read 完整描述 → (bytes, FormatId, revision = r)
Acquire(expected_revision = r) → (capability, 同一 NodeKey, r)
对调用者交付 (已验证描述, capability)
```

若描述需多块，每块均匹配 r；Acquire 不匹配就丢弃本次组合并报告 Changed。描述先由所属领域解码/校验，再取得引用。成功返回的描述与引用对应 Acquire 的同一节点修订，之后的更新不改变该结果的来源，也不保证服务仍存活。这是上层一次完整取得结果，允许多个 RPC；不要求为它建设跨节点事务或让 Read 隐式交付 handle。

基础错误区分 Changed、Unavailable、NotFound/Gone、Unsupported、Denied、Quota/资源失败及 ProviderClosed；传输中断后已提交修改的 Unknown 是客户端结果知识，不能折叠为上述拒绝。Unavailable 表示节点提供 Reference 能力但当前无可交付引用；Gone 表示节点本身已退休；Unlink 本身不导致旧 NodeAccess 返回 Gone。具体 wire 状态码在 G1 定义。

同一 NodeAccess 内不再重走原路径。需要“仍是这个名字当前绑定”的业务另持 BindingStamp，并在拥有名字权威的领域动作中作条件校验；不能声称跨 provider 的多步路径遍历是全局快照。

### 5. Reference 的权限和寿命

Reference 在安装时已经具有真实 capability owner 和确定的交付范围。Acquire 只检查 FAL 的引用取得权、预期 Revision、已安装能力的可复制性及内核运输上限，然后复制。FAL 不解释服务权限位、设备资源范围或驱动声明，也不把 transport rights 的裁剪当作领域权限衰减。

本版基础 Reference 是可重复取得的共享授权。复制品共享底层能力的身份与领域语义，不创造独立客户身份、独立付款账户或独立撤销范围。需要独立 session、排他资源申请、协议协商或单次移交的对象，公开其领域入口，由客户端直接运行那个协议；不把它们压成通用 Affine Take。这一取舍让 Reference 的取得没有隐藏的远端授权事务。

发布者/领域 owner 保证安装的引用可以按声明范围交付；FAL 验证内核可检查的权限和运输条件，不能替它证明业务 schema 或映像可信。消费端仍按领域协议验证描述。可读 Content 与可取得 Reference 分别授权；目录可见也不必具有两者任何一种权限。

移除名字阻断之后的按名取得，旧 NodeAccess 不自动撤销。owner 可把 Reference 改为 Unavailable 并推进 Revision，阻断其后的新 Acquire；已交付 capability 的撤销由实际签发者负责。节点表示的本地更新与远端资源退休不组成虚假的原子事务。

安装者持原引用，Acquire 的临时副本由该调用的回复 owner 持有；未交付就 Close，成功交付后由客户端持有。替换释放原安装引用不等于客户端副本已关闭，资源退款跟随真实占用。

### 6. `/System/` 组装与跨 provider 边界

`/System/` 是使用 Directory 组合出的树，以下名字除 Services 外只是布局示意：

```text
/
├─ Files/                     Directory，普通文件 provider
└─ System/                    Directory，namespace 装配
   ├─ Services/               Directory，服务领域 provider
   │  └─ storage              Content + Reference
   ├─ Devices/                Directory，设备领域 provider
   │  └─ controller0          Directory + Content + Reference
   │     └─ child0            Content + Reference
   └─ Drivers/                Directory，驱动声明 provider
      └─ controller_driver   Content（可另有目录或映像取得入口）
```

挂接持有目标 provider 签发的目录访问权，不复制其节点和内容。不同客户端可获得不同 namespace 根或受限子树；布局装配权本身不制造目标授权。同一设备在拓扑、分类等视图中可以被多次引用，权威设备身份仍只有一个。

跨 provider 继续 FAL 路径操作时，目标的 FAL 权利不得超过入口、调用者有效 FAL 范围和请求范围。**不能把更强的目录母授权交给不可信客户端，再要求它自己取交集。** 已满足范围的受限目录访问权可以直接交付；需要进一步收窄时，由目标 FAL provider 签发受限 NodeAccess。这个步骤属于明确的目录遍历/Open 语义，通用 FAL 只理解自己的协议，不从 Content 的领域类型触发派生。

一次跨界操作先在源 provider 捕获目标绑定及受限出口，保活该选择，再到目标 provider 取得访问权；不得持有源节点锁等待远端。挂接在捕获后被替换，已开始的操作可以完成到旧目标或失败，不能静默重新选择新目标；之后开始的操作使用新绑定。远端取消、未交付访问权和付款仍由这次 Open 的 owner 收束，wire/任务状态由 G1 接续细化。

`..` 沿调用者所走的 namespace 位置返回，不向目标 provider 索取物理父目录能力。目录中的图形关联、别名和重定向不承诺自动循环垃圾回收；每个安装绑定有明确 owner、预算及移除责任。provider 停止能封闭并解除自己持有的绑定，不以远端循环引用全消失作为停止前提。

Reference 中的任意领域入口与上述 FAL 目录继续访问是不同角色：前者按发布时确定的领域能力交付，后者必须保持 FAL 路径授权范围。不能因一个入口恰好使用 FAL 协议，就把它与自动挂接混为一谈。

### 7. 四类需求逐项落点

| 需求 | 节点与内容表达 | 实际操作路径及边界 |
|---|---|---|
| 普通文件 | 目录为 Directory，文件为 Content；文件内容任意二进制，固有长度等由 FAL 描述 | 取得稳定文件 NodeAccess 后读写；Create/Delete/Rename 修改父目录绑定。只读视图明确拒绝修改，不模拟成功 |
| 服务发现 | Services 为 Directory；每个可发现条目为 Content+Reference，Content 的服务 schema 包含实例、协议和领域状态 | 服务 owner 同点更新描述与共享入口；AcquireDescribed 组合按版本校验。需要独立 session 时 Reference 指向受限的会话入口，后续调用不经 FAL 解释 |
| 设备描述 | Devices 及可展开设备为 Directory；设备 Content 描述身份/属性/关系；Reference 可提供设备管理入口，没有公开入口时可以不提供该能力 | Read 不产生资源授权；取得入口后用设备身份申请租约。热拔后描述可保留离线状态，引用可变为 Unavailable；这不证明硬件已停止或资源可重用 |
| 驱动声明 | Drivers 为 Directory，声明为 Content；多个相关对象可组成 Directory，映像可用描述性关联或受限引用表达 | 匹配和版本规则由 libdriver 解析；绑定/启动由装配 owner 执行。可读声明不是允许执行该映像的证明 |

一个物理设备的多个关系不是目录父子所有权；上层描述可表达任意领域关系图。多个服务协议可有多个具名节点，不要求 FAL 理解它们属于同一进程。驱动更新、服务替换和设备重插分别产生领域身份变化，不能用同一 FAL Revision 替代它们。

### 8. 观察、修改和资源责任

Observe 采用**版本变化的失效通知**，允许合并多次变化；它不承诺完整事件历史。消费者用最新 Revision 重新读取或枚举。要逐条处理每次硬件/业务事件，使用对应领域协议。

订阅具有自己的 capability owner，查询/重置/取消按订阅能力鉴权，不能仅凭共享目录 grant context 加可猜 ID 操作另一持有者的订阅。建立观察时原子核对 after_revision：已经变化立即就绪，尚未变化则登记后等待；重置/确认也必须比较已处理版本，不能清掉期间发生的新变化。provider 关闭使订阅终止，不把关闭冒充正常修改。

观察结果可查询最新 NodeKey/Revision，通知只是唤醒来源；合并不丢失“至少已到这个修订”的判断。节点逻辑退休时，订阅进入 Gone 终态、唤醒并释放节点 pin；存活 provider 为它保留有界终态记录，直到显式取消或最后一个订阅 capability 消散。终态记录继续计费，不能提前退款。provider 停止则关闭服务端观察来源并释放自己的记录，客户端观察到 ProviderClosed。Rename/Unlink 通知父目录绑定变化，不使目标节点订阅假装收到 Gone。

订阅的 provider 侧资源由发起 NodeAccess 所绑定的可信账户支付，并受该账户额度和 provider 订阅上限共同约束；共享访问权的订阅可能由同一账户承担，这是显式的受限资助。独立订阅 capability 解决操作隔离，不自动建立独立付款身份。provider 不允许无准入增长，也不允许持有者通过保留终态记录超过已获额度。

Content+Directory 的 Revision 覆盖本节点的表示，目录成员改变会使对此节点的观察就绪；子节点内容变化只通知那个子节点。递归观察不是基础保证，可由上层组合且自行承担订阅资源。

名字修改由目录 owner 提交，条件针对 BindingStamp。Create 成功同时返回新绑定身份及稳定 NodeAccess；不能为使重试方便把 Create 和之后的按名 Open 混成无身份约束的两步。单 provider 内的 Rename 可原子移动绑定；跨 provider 的 Move 明确为 CrossProvider，由上层 Copy/删除协议处理，不伪装成原子 rename。

内容写入的已提交前缀、结果未知和持久性不能隐去。批量内容运输可复用 Runnel，但数据通道 EOF 不等于业务提交/持久化。精确写入、流 Finish 和 Copy 的结果类型在 G2 完成；不影响本版节点表达选择。

| 所有者 | 持有与收束责任 |
|---|---|
| 节点/provider | 权威表示、节点身份及 Revision；原引用、绑定和存储的实际寿命，停止后不再准入 |
| namespace 装配者/目录 owner | 安装的绑定、跨 provider 目录授权及其费用；移除和停止释放自己的引用 |
| 通用操作 | 临时字节、目标 pin、准备中的访问能力和回复；提交前失败全部收束，提交后回复丢失报告客户端知识上的 Unknown |
| NodeAccess / 订阅 / 客户端取得引用 | 各自独立的持有责任；Close 释放本地拥有关系，不伪称节点、订阅服务端状态或硬件资源都已完成退休 |
| 领域 owner | schema、业务状态与权限签发，领域 session/租约/绑定的准入、取消和恢复 |

付款沿可信装配或授权绑定取得；派生和复制不隐式新建账户。provider 的节点、订阅、访问记录和在途导出须按实际占用准入，页/字节、槽位和工作预算分别有 owner。这里不承诺尚未实现的逐获取者独立付款或硬隔离。

单次读取/枚举/回复按运输和内存预算分块，版本重试与路径行走有调用预算。需要多步准备时，先准备资源，提交时短暂核对身份/版本并修改本地状态；等待远端或慢存储时不持有跨 provider 锁。确切锁阶、容量推导和退款时点仍是 G1/G2 的施工门。

### 9. 取舍、反例与模块落点

| 选择 | 被排除方案及独立理由 |
|---|---|
| 同一节点可组合三种固定能力 | 互斥 Directory/Data/Reference 会让描述和入口分属不同节点，常见的一致取得需要跨节点快照；本方案把一致性放在同一 owner 的节点修订，代价是必须明确组合语义 |
| Content 为字节+格式，schema 在上层 | 递归 Value 不是这四类需求的必需语义；一字段一文件又拆散一致快照。丢失内建字段反射是接受的限制 |
| Reference 只交付已签发共享能力 | 每次取得都启动任意领域工厂，会使通用层拥有领域 RPC 和取消事务；独立会话通过已取得的入口申请 |
| 版本条件组合，基础不保留历史快照 | 自动快照/跨树事务要求所有 provider 保留历史表示及资源；本版明确允许 Changed 和有界重试，不假称持续修改下必能读全 |
| 版本失效通知 | 完整事件日志、递归订阅和业务状态枚举会引入无关历史及生命周期责任，按独立需求留在上层 |

FrostOtter 针对两种节点表达提供了反例；本轮采纳“能力集合固定”“同一 Revision 下原子更新关联内容与引用”，并由主会话补齐条件组合、跨 provider 授权及生命周期语义。未把观点当作代码证据。

官方对照补充：[Fuchsia NodeProtocolKinds](https://fuchsia.dev/reference/fidl/fuchsia.io#NodeProtocolKinds) 明确固定身份的节点可有多个打开表示；[Node.GetAttributes](https://fuchsia.dev/reference/fidl/fuchsia.io#Node.GetAttributes) 要求属性独立于访问协议保持稳定。它们支持区分身份与访问表示，不直接证明本方案的三个能力集合。[Linux sysfs](https://docs.kernel.org/filesystems/sysfs.html) 采用偏向单值/同类数组的文本属性及单次 show 缓冲，没有在该文档中承诺跨属性事务；本版保留领域自有结构化内容，避免为一致描述强制拆字段。[Windows Object Directories](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/object-directories) 明确对象目录与文件系统目录有区别；作为统一命名不等于统一对象语义的对照，不照搬其内核驻留方式。

目标知识落点：`libfal` 拥有节点/能力、Content/Reference、provider 契约及自身访问权；`libfs` 拥有 namespace 位置、路径/链接/跨 provider 组合及文件便捷操作，二者合成这里所称的 FAL 体系。`libservice`、`libdevice`、`libdriver` 消费该契约，拥有领域 schema/协议及投影。`srv_fs` 是具体 provider/装配位置，不是所有领域状态必须驻留的中央服务。

迁移时应删除旧 `NodeKind::Property/Stream` 对内容的重复分类、混合领域策略的 `ExportPolicy`、`value::Protocol::Directory` 隐式导出分支及服务 Record 的通用值依赖；现有符号的确切删除清单由 G3 对代码逐项核定。纯编码逻辑是否另有独立用途按实际消费者处理，不能保留兼容 facade。当前 libraries/README 和 impls 仍描述旧实现，实施时同步，不把本版提前回填为事实。

### 10. 本版完成范围与下一设计门

本版已选定基本表达，四类需求有明确映射；身份/绑定/版本、能力组合、内容编码边界、引用取得、一致性、观察和目录组装有可检验语义。没有留下“互斥节点还是组合节点”“Value 还是字节”“读取是否隐式签发”作为并列施工选择。

主会话按 REVIEW 的设计项进行了场景走查，以下是文档推理，不是运行测试：

| 反例 | 本版约束及检查结果 |
|---|---|
| 描述 r1 读完，入口在取得前换成 r2 | 条件 Acquire 返回 Changed；不能产生 r1 描述+r2 能力 |
| 内容分块期间更新 | 后续块立即拒绝旧 Revision；已读块作废，不与新块混合 |
| 名字删除后重建、provider 重启 | BindingStamp/NodeKey 分别变化；旧对象访问不会重定向，旧预期不会命中新实例 |
| 服务条目同时有目录、描述和入口 | 固定能力组合；名字修改只改父绑定，空目录仅检查成员，不受其他能力影响 |
| List 分页期间子节点状态变化 | 目录版本不承诺子节点快照；可变状态必须单独读取，不能用目录游标证明一致 |
| 只读 namespace 挂接写权限更强的 provider | 真正发行者签发受限 FAL NodeAccess，不能把母授权交客户端自行裁剪 |
| 两个持有者共享目录访问权 | 独立订阅能力保护查询/取消；账户仍可共享且有额度，不伪称隔离付款 |
| 热拔、撤发布及仍打开的引用 | 名字/表示变化、引用可用性、已交付能力与硬件退休分别有 owner；不由 Unlink 推断业务完成 |
| 观察建立/重置与更新交错 | 原子比较版本并登记/确认；合并后的最新修订可查询，不能清掉未处理变化 |

尚未到代码施工条件。接续必须闭合：

- **G1 剩余**：NodeAccess/订阅的 wire 和发行者认证、根/子树与每操作权利的精确矩阵、跨 provider Open 的在途取消及付款状态、路径语法与资源界，以及四个领域的最小描述协议样例。条件 Read/Acquire 的预算和端到端失败类型须落成 API。
- **G2**：修改/持久性、流/Runnel/Copy、provider 退出、实际退休/退款和锁阶的完整状态机；本版的 owner 表不能替代这些细节。
- **G3**：按实际消费者完成类型/依赖迁移图、旧路径删除清单和实施验收；设备/驱动尚无实现的部分明确为表达设计交付。

基础表达交付不把后两门降为可忽略项，也不扩大为本轮实现全部设备和驱动。未修改 ideas、Rust 或 wire；没有把任何目标行为宣称为运行证据。

## 第四轮设计：对象抽象与文件领域

用户指出：普通文件也有自己的领域知识，第三轮的通用节点模型实际上已经是对象抽象层（OAL，Object Abstraction Layer）。本轮接受这一定位校正。这里的 OAL 是用户态对象视图、命名与访问抽象，不替代内核的对象、capability 或资源隔离机制。

第三轮 Directory/Content 原意是同一节点可具备的能力，不是把每个文件拆成“目录节点+内容节点”两个实体。但更重要的问题确实存在：`Content = Bytes + FormatId` 把两种协议混在了一起：

- **对象表示/描述**：表达设备属性、服务说明、驱动声明或文件元数据，核心是可观察状态、修订和一致读取。
- **文件数据访问**：普通文件的正文及其读取、写入、偏移、长度、截断、追加、映射、同步、部分结果和持久性等契约。具体支持范围由文件领域确定，不能从“可以传字节”自动得到。

二者都能以字节运输，不代表它们是同一种抽象。第四轮不再用通用 Content 同时承诺两者，也不因删除该混合类型而预判所有对象表示只能是字节、递归 Value 或某个固定 schema。

### 当前分层

| 层次 | 拥有的内容 | 对普通文件的作用 |
|---|---|---|
| OAL 对象视图与命名 | 通用对象身份、名字绑定、目录组合、可观察表示与协议入口的共同契约；精确基础能力仍须重审 | 让文件作为对象可被命名、发现、观察并取得授权入口 |
| 文件访问/文件系统领域 | 文件种类、数据 I/O、文件会话、目录持久化及名字修改的文件系统保证 | 定义真正的文件操作，持有内容和存储责任 |
| 服务、设备、驱动领域 | 各自描述、协议、权威状态、资源和业务授权 | 与文件领域并列使用对象视图体系，不成为文件的特殊分支 |
| 应用数据格式 | 文本、图像、可执行格式等内容解释 | 普通文件可以承载各种格式，通常仍复用同一个文件访问协议 |

“文件类型”须分清：文本/PNG/ELF 等内容格式通常不改变普通文件 I/O；普通文件、目录、顺序流或设备接口等访问语义则不能只靠 FormatId 区分。是否提供类 POSIX 的特殊文件兼容视图是另一个需求，本项目不据此预设所有对象都可按文件读写。

例如 `/Documents/report.txt` 指向一个文件对象的视图；视图可以提供文件元数据和受权的文件协议入口，实际正文由文件协议读取。它不是一个名字节点再附加一个必须独立存在的“内容节点”。取得入口须绑定到所选文件对象，不能拿到一个路径字符串后重新解析到同名替代者。

`/System/Services/`、设备与驱动等是 OAL 组装的领域视图。普通文件/文件系统视图也参与同一命名空间，但其读写协议由文件领域拥有。命名目录的通用操作与真实文件系统目录的创建/删除/改名、持久化保证须明确接点；OAL 不因此成为存储事务管理者。

### 语义自描述与协议发现

用户以 `/Systems/Services/reporter/last_log.txt` 指出：仅展示 Directory/Content，首次看到对象的应用无法知道它是文件、服务记录还是设备描述。目录前缀和后缀都不能承担类型判断；此示例沿用用户路径写法，不据此改变先前 `/System/` 布局约定。**通用 OAL 必须具有统一可读取的语义描述和协议发现契约，不能只提供无类型容器。**

当前选定方向：对象的共同描述回答“它是什么、支持什么契约、怎样取得该契约的受权入口”。下列名称是概念字段，不是已定 wire：

| 描述部分 | 含义与 owner |
|---|---|
| NodeKey、DescriptorRevision | 标识描述所属对象及此份描述/接口声明的修订；OAL 拥有公共一致性契约 |
| ObjectTypeId、可读类型名 | 领域定义的语义类型，如普通文件、设备对象、服务发布记录、驱动声明；使用稳定且有归属的标识，不由路径或任意显示文本推断 |
| InterfaceOffers | 对象提供的协议标识、兼容版本及入口选择信息；OAL 承载声明与选择，协议本身由文件/服务/设备/驱动领域拥有 |
| 领域描述协议/schema | 获取该领域详细属性的标准方式；内容格式、文件长度、设备关系等由相应协议解释，不混入无边界公共字段集 |

共同描述格式是 OAL 基础契约，客户端不需要先知道某个领域的私有编码才能识别类型和发现协议。系统的文件、服务、设备、驱动领域必须同步定义标准类型与描述/访问协议，成为基础客户端的共同词汇；不能只给所有对象一个 opaque ID，再把首次识别完全推给临时插件。OAL 核心可搬运和比较这些标识，不需要按每种领域类型分派业务逻辑。标识的分配/版本规则须明确归属，不要求引入一个启动时必需的全局类型注册服务。

同一路径可以合法提供以下不同对象，名字和 `.txt` 都不决定它是哪一种：

| 实际对象 | 语义类型示意 | 声明的协议示意 | 应用如何处理 |
|---|---|---|---|
| 一份实际日志文件 | `fs.RegularFile` | `fs.FileInfo/v1`、`fs.FileAccess/v1` | 按普通文件协议查看元数据和读正文；文本格式由 FileInfo/内容识别另行确定 |
| 服务的结构化日志记录 | `reporter.LogRecord` | `reporter.LogRecord/v1` | 按记录协议解释，不因后缀而假定有文件偏移读写 |
| 同时提供文件读取视图的日志记录 | `reporter.LogRecord` | `reporter.LogRecord/v1`、`fs.FileAccess/v1` | 知道它是日志记录；通用文件应用也能按已声明的文件契约访问其文件视图 |

这里“文件还是记录”不一定互斥。语义类型说明对象是什么，接口声明说明能按哪种契约使用它，访问权限决定该调用者获准哪些操作，数据格式说明如何解释字节。四者不能合并成一个 kind、FormatId 或权限位。宣称 FileAccess 就必须兑现该版本的文件契约；字节可读不自动等于文件接口。

目录枚举应提供可识别的类型摘要（受可见性授权约束），共同 Describe 可以补全协议声明；这些动作不签发业务资源。应用流程是：定位并获得对象身份/访问根 → 读取共同描述 → 选择自己理解的协议及兼容版本 → 按同一 NodeKey/DescriptorRevision 取得对应受权入口 → 使用领域协议。对象的语义描述被移动到其他路径后仍成立。

第三轮“一个节点只交付一个无类型 Reference”的表达不能直接冻结为当前目标；同一对象支持多个领域协议时，必须有不依赖子目录命名猜测的协议声明和入口选择契约。协议 ID 是可验证的契约选择，不是 OAL 的任意业务方法调用号；独立会话及动态资源申请继续在所取得的领域协议内完成。具体 offer 表达、取得操作及付款由 G1 闭合。

描述与所取得入口必须绑定到同一对象及相容的描述修订；变化时返回明确冲突或重新描述，不能把同名替换后的入口配给旧类型信息。接口广告不是授权本身，也不保证此刻可取得或仍可用。类型/协议声明来自发布者，不构成硬件归属、代码可信性或访问权限的证明，实际交付与调用仍验证 capability 和协议。

未知的未来类型仍有可读名称、稳定标识和显式接口；如果它提供客户端已知的 FileAccess/Directory 等协议，可以按该接口使用，否则显示为有名称的未知类型并保留浏览能力，不自动当文件。通用工具不可能先验理解所有未来领域业务，但标准系统对象不能因为核心通用就失去文件、服务、设备、驱动的可识别语义。

### 第三轮结论的处置与下一步

可以按独立理由继续使用：稳定身份与名字绑定分离、描述与所取得入口对应同一对象/表示、领域授权留在签发者、namespace 组装不复制权威状态、变化观察不等于业务事件历史。文件数据版本与对象表示修订不应强行共用同一计数；对应关系由文件 provider 明确。

需要重新设计：统一语义描述的精确类型/版本规则、协议声明与受权入口取得、目录组合与各领域目录操作的分界，以及文件对象如何提供文件访问接口。通用 Describe 与协议发现已列为必需基础，不再把“是否具有自描述”留作可选。第三轮固定三能力、混合 Content、单一无类型 Reference、统一 Read/Write 和提前删除 Property/Stream 的清单均暂停作为施工结论；不能只将 libfal 改名为 liboal 后保留原有混合职责。

第四轮明确了 OAL 的抽象定位，当时尚未冻结领域库的组合；第五轮进一步确定 liboal/libfs 等知识归属和 Trait 表达。仍由本案承接，不新建平行计划、不批量改名代码、不回填尚未实现的 impls。

## 第五轮设计：Trait 对象、领域库与 provider

本节记录第五轮对 Trait、领域库和 provider 的推导。领域知识归属由第六轮继续采用，但本节曾将 Trait 一概提升为可绑定协议、将对象视图具象化为 OAL 容器，并引入跨调用身份条件和递归形状；这些已被用户在第六轮纠正，不能沿用本节示意 API 作为当前施工目标。

### Object 的公开契约以 Trait 为准

Trait 是有归属、稳定标识、版本及行为约定的跨进程协议契约，不是 Rust 内存中的 trait object 或可传输 vtable。Rust trait 可以用于实现 provider 端接口，但其布局不是 wire。声明一个 Trait 就承诺兑现相应版本的行为、数据和错误契约；拥有实现库不产生相应权限。

Object 的共同描述包含对象身份、描述修订、所公开的 Trait 及兼容版本；可携带用于展示的名称。第四轮提出的独立 ObjectTypeId 不再作为必需的第二套分类真值：RegularFile、ServiceEntry、DeviceDescription、DriverDeclaration 等领域 Trait 本身提供可识别语义，允许一个对象声明多个 Trait。分类标签如有用途，应来自领域声明，不替代 Trait 的能力契约或形成独立分派依据。

`liboal` 能 Lookup、枚举、取得共同描述、发现/选择 Trait、绑定受权入口、观察通用视图变化；具体集合及授权仍须在 G1 闭合。它不解释 RegularFile 的正文、ServiceRegistry 的注册状态或 DeviceDescription 的资源含义，也不提供一个让所有对象都可调用的 Read/Write。

一个只引入 liboal 的通用浏览器可以显示对象和 Trait 名称/版本，但不会据此调用文件读取。引入 libfs 后才能按 RegularFile 契约取得文件能力并操作。同一对象既声明日志记录 Trait 又声明 RegularFile 时，两种客户端都可以按各自已知契约使用；不能仅因一个对象能返回字节就推断其实现 RegularFile。

### 领域库同时拥有消费与提供契约

| 知识 owner | 客户端侧 | provider 侧 |
|---|---|---|
| liboal | 对象树、共同描述、Trait 发现/绑定、通用视图访问 | 通用对象/目录/provider 设施、Trait 声明与入口关联、自己的授权和寿命 |
| libfs | RegularFile 等文件领域的类型化访问、元数据及操作结果 | 同一 Trait 的协议、解码/分派契约与可复用文件机制 |
| libservice | 服务注册、发布记录、发现和提供/使用的类型化接口 | 相同服务契约、注册状态、发布授权及对象视图映射的可复用机制 |
| libdevice / libdriver | 设备描述、驱动声明及所属领域协议 | 相同领域的状态、验证、协议处理与视图实现；完整机制仍由设备分案设计 |

库按领域划分，不为每一个 Trait 建立一个包，也不把同一协议拆成互不相认的 client/server 知识库。wire 数据类型、编码、版本、错误和正常/失败/取消语义在对应领域有唯一 owner；依调用角色暴露不同 API。

目标依赖为 libfs/libservice/libdevice/libdriver 消费 liboal，liboal 不反向依赖它们。文件 provider 直接使用 liboal 的 provider 设施，同时使用 libfs 的领域契约；“libfs 已依赖 liboal”不要求 libfs 重导出或遮蔽 liboal 的全部能力。进程按自己使用的知识声明依赖。

```text
文件消费者 ──→ libfs ──→ liboal
文件 provider ──→ libfs
             └─→ liboal

服务发布者/消费者 ──→ libservice ──→ liboal
服务目录 provider ──→ libservice
                 └─→ liboal
```

以上是知识/代码依赖，不是固定进程拓扑；domain 库也可按需求直接消费 RPC、Runnel、预算和执行等公共机制。这里 `oal_service` 指服务目录 provider 的运行角色，不先要求一个同名独立库或独立进程，更不新造第二套服务协议 owner。

### 数据如何存放或提供

**OAL provider 提供对象容器和视图；领域 provider 拥有实际领域状态，领域库定义其对外数据和操作。** 同一个进程通常同时承担这两个角色，责任区分不要求多一次 IPC。

| 数据 | 谁定义对外含义 | 谁持有/提供实际数据 |
|---|---|---|
| 名字绑定、对象身份、Trait 声明及入口关联 | liboal | 提供该子树的 OAL provider，按领域 owner 的授权与寿命组合 |
| 文件元数据、正文和文件访问状态 | libfs | 文件 provider 的文件对象与存储后端；可以是内存、磁盘或按契约生成的数据 |
| 注册的服务、实例、就绪/发布状态及能力引用 | libservice | 服务目录 provider 的权威注册状态；OAL 目录/条目是该状态的视图 |
| 设备描述、关系、当前状态和授权资源 | libdevice | 设备/总线管理 owner；可以从当前权威状态生成描述，不要求先序列化进 OAL 存储 |
| 驱动声明、匹配规则及映像关联 | libdriver 及装配领域 | 声明/映像 owner，来源可为持久文件或静态装配，OAL 负责暴露其对象入口 |

Trait 规定“如何向消费者提供数据”，不统一规定 provider 的落盘格式或内存布局。协议编码、内存中的类型和持久化格式可以不同。静态描述可以复用领域编码存储，动态对象可以按其快照契约生成结果；无须先写入一个通用 Content 字段再让 libfs/libservice 读回解释。

OAL 的 Trait 入口与真实领域对象保持明确绑定，不能只保存裸 ID 后任意重建权限。通用设施可以保存/引用不透明入口及 owner，由领域实现处理方法；它不存放可任意解释的 Any/Record 后按 TraitId 自行推导字段、授权或状态转换。公共 Trait 分派边界只识别声明和目标，不理解领域方法参数。

领域状态保持唯一真值。服务注册表到目录项、文件对象到命名节点可以是直接投影或同一 owner 维护的索引；不提供两份互相独立可写的记录。Trait 调用导致领域状态变化后，由实际 owner 按约定更新视图/通知。Object 的描述修订只覆盖共同声明的变化，文件正文版本和服务状态代次仍由各 Trait 定义。

### 路径观察、单次操作与显式打开

用户指出 Lookup 可以只返回 ObjectInfo，之后由领域库对同一路径执行 Get，不必在观察时取得保活对象的 handle；同时两次独立解析可能重复走路径及 Boundary。本轮撤回“Lookup 必然得到稳定 ObjectRef，再 Bind 才能操作”的前提。第五轮的 Trait/领域/provider 归属继续成立，调用形式按以下区别设计。

| 形式 | 返回及语义 | 跨调用的叶对象状态 |
|---|---|---|
| `oal::Lookup(root, path)` | 当前所选对象的 ObjectInfo：身份、可见 Trait/版本、描述修订及适用的领域描述；可见不等于已取得操作权限 | 不隐式打开、不为结果创建需要 Close 的叶对象句柄、不保证其后名字仍指向它 |
| `fs::Get(root, path, expected?)` 等领域单次操作 | 在这次调用中解析并选择目标，校验 Trait/权限后执行；返回领域结果 | 不要求调用者先 Lookup，也不要求保留叶对象句柄 |
| `fs::Open(root, path, rights, expected?)` 等显式打开 | 解析并取得稳定对象/会话访问权，随后通过领域句柄操作 | 有明确保活、权限、费用和关闭/退出责任；不是观察操作的附带效果 |

这里的“无状态”只指调用者不持有跨调用的叶对象会话：namespace 根/目录授权、provider 树和单次请求的临时状态仍然存在。路径不是 authority，以上调用都基于调用者实际拥有的根或目录访问权。ObjectInfo 中的身份是比较条件，不是可据以重建权限的 capability。

我此前所称“稳定引用”实际更接近显式打开所得的受权句柄：用于多次访问同一对象、流会话和明确的存活责任。它应由 Open/Bind 等显式动作建立，不能未经论证并入 Lookup。具体是对象句柄再 Bind，还是领域 Open 一次取得 Trait 句柄，由真实场景决定；已知 Trait 的领域 Open 不强制先 Lookup 再 Bind。

Lookup 结果可以呈现用户举例的 RegularFile/Property/Array/Integer 信息，但须保留结构：例如对象声明 Property，值的形状是 `Array<Integer>`，而不是把元素类型误当成四个互不相关的操作 Trait。形状的定义与解释仍归相应领域库，OAL 的通用描述只按约定承载；这不把 Get 放回 liboal，也不预判完整值代数已定。

### 路径执行的解析与竞态

已知要执行的 Trait 操作时，领域库可以直接构造按路径请求。OAL 提供通用定位/Boundary 继续访问，终点 provider 在本次调用内选定并临时保活实际对象，然后把已定位的目标交给领域 handler。handler 不为了执行 Get 再从根重新解析一次；OAL 也不因此解释 Get 的参数或结果。

逻辑上可以归一为“按路径选择目标”或“使用已打开目标”，之后进入同一套 Trait 验证、授权和领域实现，不维护两套不同业务行为。跨 Boundary 的具体继续访问/运输方式留在 G1，但必须保证：只有明确尚未执行领域操作的继续解析结果才可转到下一目标；到达执行点后发生超时或回复丢失，修改类操作不能通过重新走路径而暗中重试。

`Lookup + Get(path)` 是两个操作。未给预期条件时，Get 作用于它执行时该路径选中的对象；名字在中间被替换，即使 Trait 相同也可以是新对象。调用者要求“刚才看到的那个对象”时，携带预期对象身份，必要时另带描述/数据修订；不匹配明确失败。该条件不会保活旧对象，也不使它在脱离路径后仍可访问。要持续访问原对象，应显式 Open。

两次独立从根解析会重复 walk 和 Boundary 跟随，但不是所有 Get 都必须先 Lookup。通用浏览器先识别再选领域操作时，这个成本真实存在；有明确 Trait 的调用者可直接 Get/Open，省掉独立观察那一遍。实际 IPC 数还取决于终点融合、挂接和缓存，不能把“无跨调用句柄”直接等同于总 IPC 必然翻倍。

现有 `libfs::resolve::Position` 保存最终 anchor、相对路径和摘要（[resolve.rs](../../user/libraries/libfs/src/resolve.rs)），能够复用已走到的 provider；这只是现状，不是稳定对象引用。目标设计也可以评估短期路由信息复用，但如果仍承诺“按当前原路径访问”，就必须验证相关绑定/授权仍有效。未经验证直接使用旧终点，是改变寻址语义，不能称为透明缓存。缓存不是本轮预设前置，也不因优化需求暗中给每个 Lookup 增加保活句柄。

### 文件对象的端到端使用

以下为说明依赖的伪代码，不是当前已存在 API：

```text
# 一次属性读取：已知 Trait 时无需先 Lookup
value = libfs.get(root, property_path)

# 先观察再按条件读取：ObjectInfo 本身没有关闭责任
info  = liboal.lookup(root, property_path)
value = libfs.get(root, property_path, expected_identity = info.identity)

# 多次访问同一文件：显式打开并承担句柄寿命
file  = libfs.open_regular_file(root, "/Documents/report.txt", requested_rights)
info  = file.metadata()
bytes = file.read_at(offset, length)
```

Lookup 返回当前 ObjectInfo，不隐式创建稳定叶对象句柄。`libfs` 的按路径 Get 在一次调用中定位并操作；显式 Open 则验证/协商 RegularFile Trait，取得受权的稳定访问能力，供随后调用复用。文件 provider 以 liboal 暴露对象，以 libfs 的提供端契约接收领域操作，由实际后端提供正文。

已经打开的 Trait 访问不重新按名字选择对象；名字替换后仍对应原对象或明确失败。按路径 Get/Open 若携带预期身份/修订，选定目标时核对；不匹配不能静默改为新对象。文件权限、支持操作、偏移/部分结果和持久性由 libfs 契约及文件 provider 保证，OAL 不通过解释 RegularFile 标记代为执行。

### 服务目录的端到端使用

服务目录 provider 组合 liboal 与 libservice，在 `/Systems/Services/` 这一示意挂接点暴露目录及服务领域 Trait。命名根的最终拼写是布局配置，不决定协议；本轮不通过前缀区分对象领域。

发布者可以按路径调用 libservice 的注册控制操作，也可显式绑定服务目录的注册 Trait 后复用；两者都持真实发布 authority，提交服务声明和已授权入口。服务目录 provider 按 libservice 契约准入并持有注册状态，将其映射为具名子对象。注册操作若返回领域控制句柄，其寿命由注册契约定义，不意味着普通 Lookup 也必须返回句柄。通用目录插入/任意字段写入不能绕过注册验证和生命周期。

消费者可先 Lookup 查看条目，再由 libservice 按路径读取/取得，或在已知 Trait 时直接执行；需要持续访问时显式打开相应入口。实际服务调用由所用协议库处理；客户端已直接持有某领域入口时，不要求再经服务目录发现。注销/替换改变新发现与取得关系，不替代服务自身对已建立会话的收束。

“消费者 ↔ OAL ↔ oal_service”描述的是对象访问和语义分层，不要求建立一个转发全部业务请求的中央 OAL 进程。Lookup/Describe/Bind 使用 OAL 契约；绑定后的 Trait 调用面向实际 provider，运输可复用 RPC，bulk 文件数据可按领域协议使用 Runnel。同一 provider 可以共用接收设施，是否如此不改变领域请求由领域实现处理的归属。

### 不能被“解释库”掩盖的责任

领域库不仅给字节加类型，也要定义操作效果、错误、取消、并发和寿命。文件创建、服务注册、设备租约等已提交责任由实际 provider 持有，调用者停止运行不使责任消失。一次调用的临时状态/回复 owner 与长期领域对象 owner 分开。

对象描述、Trait 入口和底层领域对象的发布/退休须形成同一责任链：解绑名字不等于关闭所有接口，关闭接口也不等于存储或硬件完成回收。OAL 自身的对象/订阅资源与领域的数据/会话资源各自计费，沿可信授权绑定付款；不能因组合两个库就重复开户或提前退款。

本轮确定知识归属、数据 owner，以及 Lookup 观察、按路径单次操作、显式打开三种访问语义。尚未冻结 TraitId/版本、路由与绑定 wire、入口真实性证明、各 Trait 的具体方法，以及跨 provider 创建/发布/停止状态机。接续先把这三种操作的共同定位/授权与完成责任落成接口，同时设计 libfs 属性 Get/文件 Open、libservice 注册/条目和设备/驱动描述；不预设每次 Lookup 都产生 ObjectRef。

## 第六轮设计：provider 投影、标签与当前路径语义

本轮用户明确以下需求，替代此前过度具象化的对象模型：OAL 是 provider 暴露内部对象视图的协议，ObjectInfo 是由 backing object 及领域信息生成的只读摘要；Trait 是平铺声明，元信息采用可扩展的带值 tag 清单。Lookup 类似 stat，Get/Write 可以直接按路径尝试；Open 的效果、所有权和仲裁由 provider 所实现的领域协议决定。不能以无关的非法组合或恶意 provider 推导额外类型系统和状态机制。

### 1. OAL 是投影，不要求独立对象实体

文件 provider 可以解析路径、读取 ext4 等后端的真实元数据，然后生成 `ObjectInfo { traits: [RegularFile, Stream], ... }`。这里 ext4 是设计示例，不是当前已经实现的后端。没有必要先创建、登记和维护一个同寿命的 OAL Object，再把文件状态复制进去。

ObjectInfo 是由 provider 生成的查询结果。文件创建作用于 fs backing，服务注册作用于服务领域状态；这些变化再通过各自的 OAL 投影可见。这个查询值本身不引入另一种可创建、占用或修改的资源。

OAL 提供进程对外暴露内部结构/对象的发现与查询协议，承担路径、目录投影及 Boundary 继续访问要求；发现之后的消费操作由相应领域协议负责。`oal::Lookup` 的正常结果不止 ObjectInfo，也可以是 Boundary。provider 是否返回 Boundary 取决于其如何暴露和委派自己的视图，不要求所有对象先经过独立 OAL 服务或对象注册。

本案的职责拆分是：原 FAL 的文件/Property/Stream 等领域协议演进为目标 libfs，通用的发现、查询和路径/Boundary 机制归目标 liboal。现有 libfs 中也有客户端走路设施，迁移必须同时拆分现有 libfal 和 libfs，而不是仅把一个目录改名。文件 provider 在实现 oal::Lookup 与 fs::Read 等按路径接口时，共用同一套后端定位和目录授权解释；OAL 不要求再造第二套对象树或遍历逻辑。DirectoryGrant 中领域相关的权限/状态不能不加区分地搬入通用协议。

OAL 的树是 provider 的内部状态/结构向外暴露的单向只读视图；根视图和挂接关系也由实际 backing/装配 owner 改变后投影出来。公共设施可以帮助实现协议和共用路径规则，不要求为每个底层对象分配 OAL 节点、身份表项或常驻能力。

全局树的可见状态来自各 provider 的真实状态；消费者取得的只是一次信息快照。不为每个进程维护隔离的 OAL 树，不因 Lookup 为它创建写时复制视图，也不因它看过对象就禁止其他进程修改。provider 内部为安全访问后端使用临时引用或短临界区，不等于对消费者授予跨调用占用。

### 2. Trait 是平铺标签，领域库解释组合

Trait 集合表达 provider 对当前目标的领域分类和形状。例如：

```text
[RegularFile, Stream]
[RegularFile, Property, Integer]
[RegularFile, Property, Array, Integer]
[RegularFile, Property, Array, String]
```

OAL 把声明作为平铺标签传输，不要求 `Property<Array<Integer>>` 这样的递归语法，也不为每种组合生成一个新的整体类型标识。标签标识须支持稳定的领域命名空间；liboal 定义通用载体及标准 tag，libfs、music_player、mime 等分别定义自己的声明。新增播放器标签不要求修改 liboal 的封闭全局枚举；具体标识编码在 G1 定义，不使用进程内类型身份充当跨进程标识。

标签组合的含义归认识它的领域库。消费者可以忽略未知命名空间的声明，按已认识的标签使用对象；不能因额外出现 MusicItem 或 Mp3 就把合法的 RegularFile/Stream 拒绝为错误形状。协议行为声明与格式标记都可作为无值标签，不要求 OAL 为它们建立不同的分派体系。

每个标签不必是一个可单独 Bind 的接口：Array、Integer 等是形状标记，RegularFile/Property/Stream 用于领域分类。具体操作由 fs 协议定义，而不是给每个标签建立 endpoint、独立版本协商和方法表。前文把 Trait 全部解释为跨进程可绑定接口的约束撤回。

合法组合由 provider 从自己的后端状态生成。libfs 按其请求契约解释组合、检查返回数据；不在 OAL 中增建针对所有可能标签组合的 schema 验证器，也不以一个故意或错误返回任意标签/任意响应的 provider 为本轮扩张架构的理由。正常的报文边界、解码和请求类型错误处理仍是协议基本责任。

### 3. Lookup 不占用，Get/Write 检查本次实际目标

当前默认接口语义为：

```text
info   = oal::Lookup(root, path)     # 可选的观察
number = fs::Get<usize>(root, path)  # 可直接调用，不消费之前的 info
fs::Write(root, path, data)         # 按本次实际目标、权限和操作语义执行
```

`Get<usize>` 由 fs 在本次请求中确认目标属于其领域、支持 Property 且是所需的标量 Integer；数组请求则按相应平铺组合及数据契约检查。没有、不可读或当前类型不匹配就报错。只要本次实际目标满足要求，即使它已替换先前 Lookup 的对象，也可以正常成功。

两次调用之间有并发窗口。Lookup 能用于展示、选择领域操作和提前发现当前形状，但不能保证下一次 Get/Write/Open 成功；后者仍须处理错误。应用已知道路径及其用途时可以跳过 Lookup。启动时 ensure 过配置文件不要求随后每次 Write 都先 stat，但也不消除后续运行中的失败可能。

本轮 Get/Write/Open 不携带此前示意的 `expected_identity`，也不自动比较旧描述修订。provider 不因先前一次观察而拒绝合法的新目标，不为它加跨调用锁或创建持久引用。身份比较本身并不等于锁或 COW，但本轮没有采用它的需求，故不把它保留成基础设计选项。

每次操作仍须对本次选定的实际目标安全执行：一次 Get 的类型检查和数据访问不能凭过期信息操作另一个不相容的后端值。这属于 provider/领域实现的单次调用责任，不形成跨 Lookup/Get 的事务，更不承诺所有文件分块读取或整个跨 provider 路径是全局原子快照。

已知领域操作可以在一次定位流程末端直接执行，不要求内部先完整 Lookup 再重新走路径。只有应用主动执行 Lookup 后再调用 Get 时，才有两次独立操作的解析成本；Boundary 路由复用是后续按正确寻址语义评估的优化，不能反过来要求每次观察都生成会话。

官方事实核对：[POSIX.1-2024 §4.16 Pathname Resolution](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html) 只在两次解析之间相关文件没有变化的条件下保证同一路径解析结果一致；普通 stat→open 不形成跨调用同一对象保证。名字被替换但本次解析/操作仍满足要求时可以成功，没有“发生过替换就必须报错”的规则。此处依据的是普通按路径接口，不声称操作系统不存在另行定义的原子操作。

### 4. 领域协议的操作效果与 provider 组合

Open 是否转移或授予某种所有权、是否建立独占访问、是否提供读写仲裁，均由 libfs 与 provider 的协议设计决定，可以有也可以没有。OAL 不预先承诺“Open 一定取得所有权”或“一定不取得所有权”，也不要求每个领域建立相同的访问会话。此前对 Open 非独占的直接断言撤回；POSIX 仅是领域设计可参考的事实，不是 OAL 的约束。

libfs 须定义自己实际提供的 Get/Write/Open/Tunnel 效果和错误，provider 对公开的契约负责。若提供游标、Append、Truncate、同步或共享访问，就按这些功能明确相应规则；需要的仲裁放在领域实现中。OAL 不解释这些操作，也不承担通用对象读写仲裁。Tunnel 与既有 Runnel 控制/数据通道的对应由领域及运输契约确定，不因此新建同义运输层。

以用户给出的 music_player 为组合场景：进程引入 liboal 实现 provider 协议，把歌单投影为目录，把歌曲投影为对象；枚举目录可返回子项名字及对应 ObjectInfo。歌曲可以同时声明：

```text
{ music_player::MusicItem, music_player::Playable, music_player::OnDisk,
  libfs::RegularFile, libfs::Stream, mime::Mp3 }
```

认识 music_player 协议的消费者可执行播放等领域操作；只认识 libfs 的消费者可将其作为 RegularFile/Stream 打开，取得该视图提供的 MP3 数据。mime::Mp3 是格式标记，含义由相应公共格式契约定义；OAL 不因它存在而实现解码或播放。

music_player 不必自己保存 MP3 数据。它可以在 fs::Open 处理函数中，将歌曲条目映射到内部记录的文件路径，再向真正的文件系统执行 Open，按 fs 协议返回结果。声明支持 fs 协议意味着对该操作结果负责，不意味着由本进程直接存储或传送所有字节。

若 fs/运输契约允许转交底层 Tunnel，可以将其返回，让消费者直接与底层传输；若需要加工数据或保持会话控制，则由 provider 实现相应中继。两者由实际公开的领域语义和授权决定，OAL 不替它选择。内部文件路径不必因此对消费者公开，OnDisk 也不是让 OAL 自动跳转到某个文件系统的指令。

一个 provider 因此可以组合多个领域协议，也可以消费其他 provider 的协议来实现自己的协议。这种依赖指向实际使用的领域库和通用 liboal；不要求中央 OAL 服务理解播放器、文件系统或 MIME。播放器是设计检验场景，不是新增待实现的正式应用。

### 5. ObjectInfo 是动态标签摘要

公共元信息采用动态 tag 清单，大小、版本、创建/修改时间不再作为每个 ObjectInfo 必须预留的固定领域字段。标准化的是 tag 的身份、含义和值类型；标准 tag 和扩展 tag 使用同一扩展机制。未提供某项信息就不包含对应 tag。

语义上，Trait 是无值的声明，CreationTime 等是带值的属性。它们可以放在一份声明清单中；wire 是否分开编码无值集合和带值条目，由后续布局决定，不额外引入对象层。以下只是摘要内容示意，尚非 wire 或 Rust API：

```text
ObjectInfo {
  music_player::MusicItem,
  music_player::Playable,
  music_player::OnDisk,
  libfs::RegularFile,
  libfs::Stream,
  mime::Mp3,
  liboal::tag::Size         => Bytes(...),
  liboal::tag::CreationTime => Timestamp(...),
  liboal::tag::ModifiedTime => Timestamp(...),
  music_player::tag::Duration => Duration(seconds = 159),
}
```

大小和时间可以来自后端文件元数据，时长可以来自播放器解析的媒体信息、索引或其他权威来源。ObjectInfo 可以组合这些来源形成一个视图的摘要，不要求每个 tag 都物理存储在同一个 backing object 上，也不要求所有信息在 ext4 元数据中原本就存在。

每个带值 tag 的定义者规定值的类型、单位和语义。例如 Size 使用明确的字节长度，Duration 使用明确的时长，CreationTime 使用统一时间表示。领域扩展的 payload 由相应库解释；通用协议只需能识别条目边界并跳过未知项，不要求理解所有领域值，更不以可扩展为由引入递归的通用 Any/Record 存储。

| tag 归属 | 负责的契约 |
|---|---|
| liboal 标准 tag | 跨领域需要共同认识的大小、时间等信息；定义公共含义和值表示，不能同一 Size 在不同 provider 下分别表示字节数、元素数或播放时长 |
| libfs / music_player / mime 等领域 tag | 本领域声明、格式及摘要属性；由对应库解释，无须加入 OAL 的封闭全局枚举 |
| 生成 ObjectInfo 的 provider | 选择、派生和组合实际摘要，保证已使用 tag 的含义与自己暴露的视图一致；不机械复制所有底层元信息 |

同一个标准 tag 在一个摘要中表达一个确定含义。若要同时呈现文件创建时间和加入歌单时间，后者使用独立的 music_player 标签，不将两个不同事实都塞进 CreationTime。修订/版本 tag 如需标准化，应另行明确覆盖范围和比较语义；它仍只是观测信息，不自动成为操作前置条件。

tag 是 backing object 到 ObjectInfo 的单向映射，可能来自 NTFS 文件属性，也可能是 provider 生成的防伪水印、派生信息或其它领域事实；映射不要求可逆。OAL 中没有“编辑 tag”这一操作对象和语义，因此不是额外制定一条禁止 SetTag 的政策，也不是待补的写入接口。实际变化通过所属领域操作作用于 backing object，之后按 provider 的投影得到摘要。provider 在内存中构造 ObjectInfo，不使这个返回值变成独立可编辑的对象存储。

只读摘要不是冻结底层：文件内容变化可以使 Size 和修改时间变化，媒体信息更新也可以改变 Duration 等标签；先前返回的 ObjectInfo 不控制这些变化。OAL 无需为此维护第二份可写元数据，也不承诺不同来源摘要与后续领域操作之间有事务一致性。

### 6. 当前知识归属与撤回项

保留 `libfs/libservice/libdevice/libdriver → liboal` 的依赖方向，并允许应用定义独立的协议库与标签命名空间。领域库定义声明、带值 tag 和操作的消费/提供端契约；实际 provider 从自身及所依赖的 backing 状态生成视图，也可转发领域调用。liboal 拥有通用协议载体与公共 tag 契约，不拥有所有标签的语义或领域数据。共享传输/执行设施不因此获得领域状态。

明确撤回作为当前前提的设计：持久 OAL Object 注册表、CreateObjectInfo、观察即取得对象能力、逐标签接口绑定、强制身份/描述版本匹配、递归类型语言、按进程保存隔离对象树，以及为任意坏 provider 建立完整标签证明系统。前文有关这些内容仅保留为被替代的推导，不进入施工清单。

### 7. OAL 仍待闭合的协议契约

当前已定的是单向视图、动态只读摘要、领域独立消费及按当前路径操作。剩余工作集中在发现协议本身，以下项目闭合即可登记 OAL 基础协议设计完成；不要求先决定 fs 的全部业务语义，也不代表全案或代码交付完成。

| 项目 | 需要落定的契约 |
|---|---|
| 路径寻址与共用走路 | 根/目录入口和相对路径的表达，组件、父路径及链接的规则；OAL 通用路径约定与 provider 实际解析的接点，使 Lookup 和领域按路径操作共用机制 |
| Lookup 与 Boundary | `Found(ObjectInfo)`、Boundary 及错误的结果模型；Boundary 的继续访问入口、消耗位置/剩余路径、恰好命中边界时的行为与继续访问上界。具体字段表示仍待选定，不同时存放可互推的重复真值 |
| 向领域协议接续 | 最终 provider 入口与相对路径怎样用于 fs::Read 等调用；同一入口怎样识别领域协议；目录授权如何同时服务发现与领域操作。复用现有 RPC/能力运输，不默认每个 tag 都要 Bind，也不强制应用先 Lookup |
| 枚举 | 子项名字、ObjectInfo 及边界项的呈现，分页/结束/游标失效规则；目录变化时的结果约定，不默认建立快照或为每个进程保留一份树 |
| ObjectInfo/tag 的线形 | 稳定命名空间标识、无值/带值条目边界、标准 tag 值类型和单位、未知项跳过、重复键及摘要超出响应预算时的行为；不把单向 tag 反解成后端写操作 |
| 调用完成与失败 | 路径错误、不可发现/拒绝、provider 消失等错误边界，期限及有界解析/响应；沿已有 RPC 和能力运输处理取消及 Boundary 所转移入口的接收/释放，不引入 OAL 叶对象寿命 |

Boundary 的继续访问与 provider 内部转发必须分别说清楚。前者让调用者转向另一个发现入口；后者由当前 provider 回答自己的视图，再由它实现领域操作。music_player 可以两者都支持，也可以只用其中一种。跟随 Boundary 后由哪个 provider 生成最终 ObjectInfo，以及是否保留任何路径来源信息，须明确；不能默认把沿途所有 tag 自动叠加。

若播放器希望最终摘要保留自己的 MusicItem/Playable 等声明，它可以自己回答 ObjectInfo，在 Open 内部调用文件系统；若返回指向底层文件系统的 Boundary，则发现继续到该目标，其最终摘要按该目标的投影产生。需要保留复合视图时，可委派给能提供该视图的 provider；OAL 不自动替不同 provider 合成领域摘要。

已查现有源码：[resolve.rs](../../user/libraries/libfs/src/resolve.rs) 具有 Found/Delegate/Link、目录入口和相对后缀；[backend.rs](../../user/libraries/libfal/src/backend.rs) 的 lookup/resolve 复用 lookup_child；[route.rs](../../user/libraries/libfal/src/route.rs) 表达委派目标与剩余路径。这些是拆分时的现状依据，不是要求保留旧 NodeSummary/FalRights/NodeRef 混合结构、旧限额或两套顶层遍历。共用机制也不等于预先固定每个操作的 IPC 次数。

下一步先写路径寻址、Lookup/Boundary 以及领域接续的最小完整协议草案，用普通 fs provider 和 music_player 的“内部转发/返回边界”两种情况走通；再定枚举与 tag 编码。fs 的 Open 所有权、仲裁、数据操作和复杂完成语义由 G2 单独推进，不再作为 OAL 对象模型的待决项。

## 第七轮：从旧 FAL 拆出的三组协议草案

用户要求据旧 FAL 继续形成 OAL、fs 和可扩展服务目录的具体设计。本节是当前可审阅方案，承接第六轮的单向视图约束；以下协议及行为是目标设计，不是现有代码事实。不把旧协议照搬当作理由，也不再从零发明对象模型。完整设备资源、驱动运行和正式进程装配仍由各分案拥有。

### 1. 职责与复用依据

| 旧机制 | 目标归属与处置 |
|---|---|
| 路径组件、客户端走路、Lookup 委派/链接、相对目录入口 | liboal 的路径与发现契约；从现有 libfal 和 libfs 两处抽取，统一客户端/提供端规则 |
| 固定 NodeInfo/NodeSummary | 由 OAL 的动态 ObjectInfo 替代；文件标签由 libfs 定义，不保留统一 NodeKind 或强制对象身份/版本字段 |
| Property/Stream、目录变更、文件权限、文件 DirectoryGrant、流控制 | 合并到目标 libfs；消费 OAL 路径契约，共用自己的后端 resolver |
| ServiceRecord 伪装为 Property/Record，Read 时导出 endpoint | 删除该表达；服务摘要为 OAL 投影，取得入口是 libservice 的显式操作 |
| 服务名字授权、发布控制、就绪/撤出、endpoint 失效观察 | libservice；登记表直接拥有注册资源并生成视图，不再依赖 FAL NodeStore |
| Directory 特制 ExportPolicy、属性中的能力值及 affine Take | 不进入 OAL/tag 或 fs Property；真实能力交付由领域操作和 RPC 承担，旧探针随迁移移除 |
| 文件 Watch、Copy | 保留有独立用途的文件能力，按下文归 libfs；服务变化订阅归 libservice，不让服务目录冒充文件 |
| 通用 LE Reader/Writer | 移到 librpc 的协议编码工具模块，由 OAL/fs/service 直接使用；不为共享字节游标保留 libfal 或建立 fs→service 依赖 |
| RPC、Runnel、来源登记、预算 | 复用各自 owner；不新建通用 OAL 运行体或第二种流运输 |

目标依赖为 `libfs → liboal + librunnel`、`libservice → liboal`，二者均可直接消费 librpc/libexecution/libbudget/libkernel；libservice 不依赖 libfs。music_player 可以同时消费 liboal/libfs 并实现自己的协议。设备/驱动库按相同方式定义标签和领域操作，不使 OAL 增加领域分支。

核实依据：现有 [RPC 前缀](../../user/libraries/librpc/src/lib.rs) 已用消息 kind 承载协议标识，但当前 srv_fs 实际使用不同 ingress/邮箱分开接收 FAL、注册和路由协议；目标的多协议视图入口需要调整宿主分派，不能称为现成实现。现有 [Move 准入](../../user/services/srv_fs/src/server.rs) 从附带 capability 经 GrantTable::validate_received 校验目的目录，目标 Rename 可以复用这条可信授权路线，不从裸路径/整数重建授权。

### 2. OAL 的入口、路径与共用走路

`ViewEntry` 是遵循 OAL 路径调用约定的真实 mailbox sender；服务端根据 sender context 取得自己的授权根、发现权限和领域上下文。它不是 ObjectInfo，也不是每个叶对象的持有引用。根入口由装配交付，Boundary 可以交付另一个已经按实际范围授权的入口。

OAL 定义 `Traverse/Lookup/Enumerate` 三项发现权限的含义；是否准许由 provider 的入口上下文判断。fs DirectoryGrant 在同一个上下文中组合这些发现权限及 FsRights；它的根、后端引用、文件权限和账户仍由 fs 拥有。服务目录使用自己的上下文。普通领域调用只要求实际路径遍历及对应领域权限，不被迫先取得查看摘要的权限。

Boundary 的输出授权须与当前请求的实际范围相容，不能将过宽的下游母入口交给受限调用者，再附一份要求客户端自觉遵守的 rights。provider 可选择预先签发、适合本次上下文的入口；若 fs 的受限 DirectoryGrant 需要继续衰减下游文件权利，由 fs 的边界处理逻辑向真实文件发行者调用 DeriveDirectory。OAL 只承载最终入口，不理解 FsRights，也不以运输 rights 裁剪代替领域衰减。无法兑现本次范围则明确拒绝。准备中的下游授权归本次请求 owner，取消/交付失败沿 RPC 清理，不能遗留无人持有的 grant。

路径采用按 `/` 分隔的字节组件，不要求底层名字能表示为 UTF-8；文本 SDK 可提供 UTF-8 便利入口，显示时的转义不改变实际名字。NUL 非法，空相对路径表示入口本身。客户端接受绝对路径与选定根内的相对路径；重复分隔符按一个处理，尾分隔符要求目录，`.`/`..` 在走路过程中处理，不能在解析链接前消去尚未确认的 `x/..`。达到调用根后再上行返回 OutOfScope。

发给 provider 的路径是规范化的相对片段，不含 `.`/`..`；遇到需要父级处理的组件时，客户端先确认已走位置，再使用自己的路径帧回退。跨 Boundary 的父级是挂接位置的逻辑父级，不是目标 provider 授权根之外的后端父级。链接的绝对目标回到调用者原来的根，不能产生调用者原本没有的入口权限。末项是否跟随链接由 FollowFinal/NoFollowFinal 规定，前缀链接始终处理。

provider 仅实现一份实际定位机制。它返回本次调用的本地目标，或提供继续走路的 Boundary；OAL Lookup 调用摘要生成，fs Read/Get 等交给相应领域 handler。允许本地短期引用保障一次调用，不建立 OAL 对象表，不给查询结果增加跨调用寿命。

### 3. 路径请求与领域请求的接续

视图入口上的路径请求采用共同前导，其后仍是本领域的请求体：

```text
mailbox kind = OAL / FS / SERVICE / 应用协议的独立 ID
payload      = RpcPrefix | PathHeader | relative_path | domain_request
```

PathHeader 的字段为：路径格式版本 u16、路径 flags u16、已有 Deadline 编码、path_len u32、max_reply_bytes u32；整数 little-endian，path_len 只界定路径，剩余字节交所属领域解码。flags 明确定义 NoFollowFinal、RequireDirectory 和 NoContinue，其余位须零；缺省跟随末项。业务版本/opcode/参数留在 domain_request；OAL 不解释它们。第一版路径格式版本为 1，未知格式或 flags 拒绝。单一前导承担路径和期限，不在领域体重复保存同一份路径/期限。

响应同样先经 RPC 匹配，再得到 `Done(domain_response)`、`Continue(boundary)` 或 `PathError(code)`。Done 后的状态和值由领域协议解释。只有在尚未调用业务 handler 时才能返回 Continue；所以无输入能力的 Get/Read/Write/Open 可以直接从根发起，跨边界继续请求，终点执行业务，无须先返回一次完整 ObjectInfo。

provider 的宿主先根据入口上下文做通用路径走路，到达本地目标后按消息 kind 调用已注册的领域处理器；不认识的终点协议返回 UnsupportedProtocol。OAL 库只拥有路径前导、结果和走路工具，实际领域分派表由组合这些库的 provider 宿主拥有。OAL-only 的中间 provider 可以返回 Boundary，不必链接所有下游领域库；它不能执行或改写未知业务体。

这里的自动继续仅适用于无业务输入 capability 的请求。Rename 等携带授权的路径动作先用 Locate 定位，再带 NoContinue 显式发送一次领域调用；Register 直接使用已取得的发布 authority 入口，不是 OAL 路径动作。最终调用又遇到 Boundary 时返回未执行业务的 RouteChanged，不重新投递。初版这些请求携带的是为本次调用准备的可共享能力副本，原目录授权/被发布入口仍由调用者持有；失败时接收端关闭收到的副本。未来消费 affine 输入的协议须自行定义未执行时的返还与回复失败责任，不能套用这条副本合同。到达执行点后超时或失联均不以“重新走路”自动重试修改操作。

会话控制、注册控制及直接服务入口不必使用 PathHeader；它们使用自身 endpoint 和协议。路径前导是视图入口的协议约定，不修改 librpc 的通用前缀，也不把每个普通 RPC 强制包进 OAL。

### 4. Lookup、Boundary 与枚举的确定行为

OAL 操作为 `Locate(path, require_directory)`、`Lookup(path, follow_policy)` 和 `Enumerate(path, cursor, reply_budget)`。Locate 只要求 Traverse：本地 Done 返回空的 Located 确认，由客户端保留本次已有入口和相对路径；不生成摘要、不执行业务、不创建叶对象句柄。RequireDirectory 用于确认 `..` 前的位置、父目录和 Rename 两端，失败返回 NotDirectory。它与 Lookup 共用走路，但不因缺少摘要读取权或 SummaryTooLarge 而阻断本来获准的领域操作。

Lookup 的本地 Done 体为完整 ObjectInfo。定位结果和摘要都不承诺下一次操作仍命中同一对象；目录在 Locate 与 Rename 之间改变时，Rename 仍校验本次实际后端目标与授权。客户端处理 `a/../b` 时先以 Locate/RequireDirectory 确认前缀，而不是提前对 `a` 执行 Write 或额外要求读取摘要。

Boundary 有两种表达，来源于旧委派和链接机制：

- `Delegate(consumed_bytes, next_entry)`：next_entry 经 capability slot 交付；剩余路径从请求按组件边界切分得到，不再重复传 remaining。恰好命中委派位置仍返回 Delegate，下一跳相对路径为空。
- `Redirect(consumed_bytes, base, target)`：base 为当前链接的父位置或调用根；替换已经消费的链接段，再接原剩余路径。它不交付新的权限。NoFollowFinal 命中末项链接时 provider 返回该链接的摘要，不发 Redirect。

每轮都减少客户端的剩余调用/展开预算，采用一个总 deadline；路径字节、帧和下一跳入口占用均计入调用预算。预算从运输容量及调用者配置产生，旧 40/256 等数字不直接成为协议常量。耗尽返回 WalkLimit，已接收的临时入口由当前走路 owner 关闭。

委派后的最终 ObjectInfo 由最终应答 provider 生成，沿途摘要不自动累积。播放器自行回答音乐视图并内部转发 Open，或将路径交给其它 provider，均遵守这条规则。

枚举返回 `(name, summary_result)` 的页以及不透明 next_cursor/End。summary_result 是 ObjectInfo 或该项摘要不可用的错误；边界项用标准 Boundary 标记表达本地所知信息，不在枚举时隐式遍历所有远端子树或为每项交付 grant。消费者 Lookup 该名字时才继续走路。

cursor 由 provider 编码，可使用后端原生游标，不强制字节序排序或建立内存索引。目录不变时须可有限分页遍历且不重复；变化时允许漏项/重复，游标不再适用则返回 CursorInvalid。游标不是授权，不能改变请求根；不建立默认枚举快照或每客户端对象树。一项摘要过大可报告该项 SummaryTooLarge，其余项仍可枚举，不把截断伪装为完整摘要。

### 5. ObjectInfo 的线形与标准标签

ObjectInfo 是条目序列；每项为 `namespace[16] + local_id:u32 + value_len:u32 + value[value_len]`。命名空间为协议包固定的 128 位标识，第三方可自行分配并在包中固定；OAL 不维护运行时中央标签注册表。标准包标识和 local_id 在各自协议模块保持唯一常量，变更含义须使用新标识。无值声明的 payload 为空；空字符串等带值 tag 仍按其键的已知类型解释。

同一摘要中键唯一；顺序无语义，不要求 provider 排序。解码器验证条目边界和重复键，未知键按 value_len 跳过，不推理不同领域标签的组合合法性。tag 中不承载活 capability；业务入口经领域调用和 RPC capability 槽交付，描述性 ID 不成为授权。

首批标准 tag 为 Directory、Boundary、Size、CreationTime、ModifiedTime、SummaryRevision。Size 为逻辑字节长度 u64；时间为 UTC epoch 秒 i64 加纳秒 u32，缺少可靠时间就省略；SummaryRevision 为可选的不透明摘要修订，仅描述该 provider 视图的摘要变化，不代表内容版本、对象身份或 Get 前置条件。无可靠修订来源时省略，不为填 tag 创建 OAL 状态。

fs、service、music_player、mime 等自行定义命名空间与 tag 值类型。fs 的 Property/Array/Integer 等仍是平铺标记；一个 tag 的值类型不自动变成整个对象的新 Trait。完整 ObjectInfo 必须在一次有界响应内编码；过大返回 SummaryTooLarge，完整领域记录或正文通过领域协议获取。标准 tag 是摘要语义，不是可反向映射的属性存储。

### 6. fs 的基础接口与类型

libfs 同时拥有消费端、提供端、文件权限与后端契约；它的 OAL 实现从同一后端生成摘要。目录声明 OAL Directory 和 fs Directory；普通数据对象声明 RegularFile 及 Property 或 Stream；链接声明 fs SymbolicLink。文件后端中的实际状态决定这些标签，不储存另一份可编辑 Trait 集合。

| 操作 | 明确语义 |
|---|---|
| Get<T>/Set<T> | 完整读取/替换有类型 Property；检查本次实际目标。Set 可改变 Property 值形状，随后的摘要自然改变；不是修改 tag |
| ReadAt/WriteAt | 对 Stream 在明确偏移执行有界字节访问；返回实际字节数，支持短读/短写；普通 Write 不隐式创建或截断 |
| Open | 按当前路径建立指定方向/范围的文件流会话，返回控制入口和 Runnel offer；不带先前 Lookup 的 expected_identity |
| Create | 在已定位父目录中独占创建 Directory、Property、Stream 或 SymbolicLink；名字已存在报 Exists |
| CreateOpen | 独占创建 Stream 并在同次成功结果取得其流会话；用于避免 Copy 在创建与按名打开之间操作到别人替换的文件 |
| Remove/Rename | 对实际目录名字操作；非空目录不递归删除。Rename 校验两个真实目录 grant，在同一 provider 原子提交；跨 provider 返回 CrossProvider，不暗中 Copy/Delete |
| ReadLink | 在 NoFollowFinal 下读取链接目标字节，属于 fs 的链接操作；不要求调用者通过摘要读取权取得目标 |
| SetLength/Sync | 前者改变逻辑长度、扩展部分读为零；后者单独请求持久化，后端不能兑现时明确 Unsupported，不能把内存接收当作持久完成 |
| DeriveDirectory | 由文件 provider 签发受限目录 grant，范围和文件权利不超过来源；发现权限和 FsRights 分别检查 |
| Watch | 显式订阅文件/目录变化，返回独立控制入口；不使用共享目录 grant 的裸订阅 ID 充当唯一管理权限 |

Property 值的初版编码支持 Bool、Signed64、Unsigned64、Float64、UTF-8 String、Blob 及这些类型的同质一维数组；不包含 capability/ServiceRecord 或通用递归 Record。Get<usize> 接受 Integer 并做范围检查，标量/数组不相容则 TypeMismatch。值编码由 fs 拥有，ObjectInfo 只给平铺形状摘要；完整值受一次 RPC 原子替换/返回的容量约束，超出返回 ValueTooLarge。

fs 根入口上下文拥有 FsRights、后端根和可信付款绑定。旧 GrantTable 的按接收能力验证目的目录的机制用于 Rename，源/目的授权不能由客户端填写的身份代替。验证 sender 属于本 provider 后，还须检查源 REMOVE、目的 CREATE/替换权限、实际目录类型和目录循环条件；身份校验不能替代这些业务检查。PathHeader 只定位一个请求目标；Create 定位父目录，Rename 由 SDK 先 Locate 两端并携带目的目录授权，业务 handler 校验后再提交。

Get/Set 对一份实际值线性化；小 ReadAt/WriteAt 与其它对同一文件的操作以本次有界数据提交为单位串行化。共享流按块推进，不承诺整个文件或整个流的原子快照；重叠写以实际提交次序决定结果。实现可用单一 owner 或后端短临界区，不能持锁跨远端等待。长数据处理按预算分段，文件名变更不把已选定的会话改指其它对象。

初版 fs 选择共享访问会话，不转移文件归属、不提供隐含排他锁；这是本节选定的 fs 契约，不是 OAL 的要求。不同 Open 具有独立范围/进度。若未来提供排他或所有权转移，须由 fs 的显式操作定义，不能仅凭摘要 tag 推导。

首批实现支持矩阵：内存文件 provider 提供目录 Create/Remove/Rename/Derive、Property Get/Set、Stream 小 I/O/Open/CreateOpen/SetLength、链接 Create/ReadLink 及文件 Watch；Sync 明确返回 Unsupported，不宣称内存文件持久化。服务目录实现发现、GetEntry、注册控制和服务订阅，不实现文件接口。播放器仅是组合检验例，可实现只读 fs Open 与自己的播放协议，不因此必须实现 Set/Create。Unsupported 表示对象/provider 不提供该操作，Permission 表示实现提供但本次授权不允许，两者分开。

### 7. fs 流完成、Watch 与 Copy

复用现有 Offered → Active → Terminal 的控制过程及 Runnel 单工数据面。Open 成功先交付控制入口/offer；客户端建立映射并按 Runnel 准备后 Start，provider 才执行传输。offer 有有限建立期限，未 Start 的退出/超时释放预备占用。Active 会话按显式期限及端点存活收束，控制入口持有已选择的后端文件。

读流的范围由 Open 时的起点及上界确定；内容可以被其它写入改变，截断可能导致提前 EOF，不伪装成固定内容快照。写流的 accepted 是已进入后端的前缀，transported 是运输进度，两者不混淆。Finish 等待 EOF 被正确排空及业务处理完成；Cancel 保留已接受前缀，并在已提交的后端工作确定收束后给出终态，不能在仍可能提交写入时提前宣布最终计数。读取方向的对端接收计数只表达已经确认的消费进度，Copy 以自己的实际读出量另行计数。Sync 的持久性要求与 Finish 分开。映射/来源撤销失败由会话退休 owner 继续处理，不能因回复、取消或关闭控制入口就提前退款。

Watch 由文件协议拥有，服务目录另有服务变化订阅。两者复用底层通知/来源登记和单调计数工具，不再共同依赖文件 NodeStore。每次变化递增 sequence 并合并事件位；Query 不清空，Ack(sequence) 仅在未出现更晚变化时清除，否则保持通知，避免 Query/清除之间丢唤醒。事件是重查提示，不是完整日志。fs Watch 绑定所选后端文件/目录，其退休、明确撤销订阅授权或 provider 停止给出终态；服务按名字/目录订阅的终止条件见下文，不能因某次 publication 退休就终止它。独立控制入口关闭后取消订阅并最终释放资源。

消费者顺序固定为：先建立订阅，Query 订阅得到 sequence，再读取/枚举实际状态，最后 Ack 这个旧 sequence 并等待通知；不能在状态读取之后取一个更晚的 sequence 来确认，否则会吞掉中间的变化。序列耗尽时明确终止订阅，不回绕复用。

Copy 是 libfs 客户端组合：Open 源、CreateOpen 目标、按预算搬运、分别完成两端。源内容不是默认快照，目标是本次创建并打开的文件；名字随后改变不把会话转向替代者。结果分开记录本地读出量、提交到运输的量、最后确认的目标 accepted，以及两端可缺失的终态；只有收到目标可信终态才能报告精确最终 accepted。失联时最后确认值只是下界，最终写入/完成可以未知，关闭映射不补足这个知识。初版保留已经创建的空文件或部分结果，不自动按原路径删除。源、目标会话及映射由 Copy owner 全部收束；文件本身仍归后端，保留结果不是泄漏。

发送 CreateOpen 后丢失结果时报告创建结果未知，不自动重试、按名字清理或宣称回滚。这个选择替代旧 CreatedTarget 的默认条件删除路径；它不需要跨 Lookup/Get 身份匹配。是否另提供显式临时文件/原子发布由独立文件需求触发，不是当前 Copy 成功或失败责任的缺口。

### 8. 服务目录的协议与单一真值

服务目录 provider 直接拥有名字索引和 Publication，不再持有一棵 FAL 投影 NodeStore。OAL Lookup/Enumerate 根据当前可见注册生成 Directory/ServiceEntry、协议声明及其它服务摘要 tag；不伪装为 RegularFile，也不在摘要中导出 endpoint。客户端认识 service 标签时调用 libservice，不认识时仍可浏览名字和已认识的公共摘要。

| 接口 | 语义及授权 |
|---|---|
| DelegateName | 持管理 authority 者签发限定名字的发布权；它与发现根入口分开，不因目录可见而获得 |
| Register | 凭发布 authority 提交目标名字、协议描述、可共享入口和有限建立期限，返回 PublicationControl；只进入 Starting，不公布名字 |
| Publish(CreateOnly/Replace) | publication 的控制者声明入口已准备好；CreateOnly 要求名字空闲，Replace 要求发布授权允许替换；一次提交名字指向 Ready publication |
| GetEntry(path, protocol_requirement) | 在本次调用中选取 Ready publication，返回匹配的协议描述、publication 标识和同一条目的入口副本；不依赖旧 Lookup，不创建业务会话 |
| BeginDrain/Withdraw | 经 PublicationControl 停止该 publication 的新取得，并从名字索引移除它自己的绑定；旧控制者不能移除替代者 |
| QueryPublication | 经控制入口查询自己 publication 的状态及终止原因，不通过重查名字寻找旧实例 |
| WatchDirectory/WatchName | 服务领域的变化提示，使用独立订阅控制入口；订阅建立先于首次查询，并用上述 sequence/Ack 规则消除丢唤醒窗口 |

WatchName 绑定已授权目录中的名字，允许名字暂不存在，并跨 publication 替换持续有效；调用目标是目录，名字作为服务参数，因此不依赖先 Lookup 到某个服务条目。WatchDirectory 绑定目录范围。发布、替换和撤出仅产生变化提示；订阅的终态由取消、其授权范围明确失效、目录本身退休或 provider 停止决定。单次 publication 的状态通过自己的 PublicationControl 查询，不拿它的寿命代替名字订阅寿命。

Register 接受的是目录内单个名字；管理 authority 规定允许的名字范围及 Create/Replace 权限，控制入口持有准入时授予该 publication 的范围和权利。关闭发布 authority 的某个别名不等于撤销已经交付的注册控制权。GetEntry 返回的协议描述须描述该入口实际接受的协议及路径调用约定，不把某个工厂/准入入口伪装成已经建立的业务会话。

状态为 Starting → Ready → Draining → Terminal。Register 可准备多个有相同目标名字的 publication，实际名字竞争在 Publish 提交时决定；CreateOnly 失败保留 Starting，调用者可继续管理或关闭。Replace 原子更换可见条目，并使旧 publication 进入 Draining；旧 publication 的控制、已发出的入口和费用不因此冒充已经回收。对同一已 Ready publication 重复 Publish 返回当前结果，不恢复已被撤出的注册。

Starting 到期、控制入口消散或被注册入口关闭时，由 registry 停止发布并收束；Ready 失效同样撤出自己的绑定。名称删除只在索引仍指向本 publication 时生效，这是注册资源自身的清理责任，不是用户 Lookup 后锁定对象的机制。Terminal 后只保留必要控制终态，真实入口、观察来源及临时交付引用逐一退休后才退款；控制入口最后关闭后释放终态记录。

GetEntry 的选择与获得副本在 registry 的一次受保护步骤完成；它返回的描述和入口对应同一个 publication。此后撤发布只阻止新选择，已选定/已交付入口按其发行者的业务协议存活；registry 不承诺召回它们。若请求已投递但结果丢失，调用者按既有 RPC 未知结果处理，不据此创建虚假的新实例。

注册的入口必须是发行者允许重复共享、实际权限已经限定的调用入口。registry 只复制其被允许的运输权，不理解或衰减 FsRights，不向文件 provider 隐式请求 Derive。需要独立文件授权/业务会话时，发布实际的领域准入入口，客户端 GetEntry 后调用该领域协议；固定共享入口不能被声称为逐客户端隔离会话。付款由可信发布/发行上下文绑定，不接受请求中的裸账户 ID 作为付款授权。

PublishReady 是发布者的就绪声明，registry 不探测任意业务协议，也不根据 endpoint 存在推断业务健康。谁启动、监督、重启以及怎样确认真实就绪由正式装配分案拥有；registry 只兑现发布与取得关系。首轮可以由现有进程组合 fs provider 与 registry 模块，不预设必须新增 srv_oal/srv_service。

### 9. 正常、失败与资源交接

| 责任 | 准入/提交点 | 失败、退出与最终释放 |
|---|---|---|
| 路径发现和 Boundary | 请求 owner 持路径帧；提供者授权后准备继续入口 | 未发送/未采用的能力由请求清理；采用后归走路 owner；超时释放临时帧，不产生叶对象会话 |
| Property/目录变更 | 内存/配额准备完后，由后端原子提交值或名字变更 | 提交前可回滚准备；提交后回复失败不回滚，不自动重放 |
| 文件 Open/CreateOpen | 预留文件/会话/运输资源后建立可交付结果；CreateOpen 的名字插入是创建提交点 | 丢失回复时控制/offer 经寿命观察及期限退休；已提交文件保留，结果未知须报告 |
| Publication | Register 持真实入口及控制资源；Publish 才提交名字可见 | 未发布回复失败可关闭预备资源；发布后失联由已登记观察/期限接管，不依赖发布者继续调用 |
| GetEntry | 选定 publication 并准备对应入口副本 | 交付失败清理副本；成功后由消费者持有，发行者拥有业务资源；撤名不提前退款仍存引用 |
| 订阅/流会话 | 各领域显式建立资源并注册既有来源观察 | 端点关闭/超时触发当前 owner 退休；清理待办继续被 provider 持有，真实释放后退款 |

新协议不重建 RPC、执行或来源登记。当前实际 server 对每协议设 ingress；迁移后视图根入口由宿主按消息 kind 分派，独立控制入口保持各自角色。已有 RpcPrefix、slot 0 回复授权、业务 slot 1 起、PreparedResponse/Outbox 和失败返回完整 packet 的机制继续作为运输依据。root、会话、publication 和 subscription 的账按真实 owner 计，不给 ObjectInfo 或每个 tag 另开户。

### 10. 跨领域走通与迁移顺序

普通文件：根入口 → FS 路径请求 → 共用走路遇到 Boundary 则继续 → 文件 provider 本地定位 → Get/Read/Open；显式 Lookup 走同一定位后生成摘要，不是必经前置。播放器：Lookup 生成音乐/fs/MIME 组合摘要，fs Open 由播放器执行并转发，或 Lookup 直接委派给能提供目标视图的 provider；这两种情况不改 OAL。

服务：发布者 Register/Publish → registry 名字索引生成 OAL ServiceEntry → 消费者直接 GetEntry → 调用实际领域入口。文件 provider 的 DirectoryGrant 可以作为已限定的共享入口发布，registry 无文件特例；要求独立 grant 时由文件准入协议处理。设备与驱动的描述同样通过 OAL tag 暴露，Lease/Bind/Start 等操作留在其领域；没有文件 Get 或服务注册作为它们的强制前置。

实施按同一契约切面迁移：先路径前导/Boundary/摘要及 provider 分派，再合并 fs 的协议与后端、迁移 registry 及 GetEntry，最后接通正式消费者与清理旧路径。实际消费者为 srv_fs、srv_init、test_fal 及两个库内部调用；不能以旧探针作为保留 Handle Property/Take 的理由，也不能为测试先建音乐播放器或设备假服务。

原发现链 `subscribe → Read → ServiceRecord::decode → endpoint` 改为 service Watch → GetEntry；原 fs 客户端走路改为共用 OAL 路径调用，去掉常规操作的 expected_identity。删除 libfal 包、旧固定 NodeInfo、服务 Property/Record、Directory ExportPolicy 特判和 affine Take 路径；现有文件后端必要的节点/名字/流状态留在 fs，不因删 OAL 对象模型误删真实后端状态。

迁移须同步 Cargo 身份/依赖、导入、启动交付、实际测试和 impls；设计阶段不把目标写成 libraries/README 或 impls 的既成事实。协议数值常量、路径前导及各操作的完整编码表在实现前集中到各 owner 的协议模块；不保留同一字段的多个定义。

本轮语义审阅重点：跨 Boundary 的无副作用继续、同一 grant 供发现和领域操作、未知 tag 不影响已知协议、摘要不导出能力、旧 publication 不能撤掉替代者、共享入口不伪装成独立授权、EOF 不冒充业务/持久完成，以及取消 Copy 不删除同名替代者。设备完整设计、真实存储后端和正式装配不在本轮交付范围；OAL/fs/服务目录的上述基础协议已形成一套具体草案，尚未执行代码或平台验收。

### 11. 本轮设计结构复核

只读独立审阅提出三项具体缺口，均在本节模型内修正：补 Locate，使仅有 Traverse 的 `a/../b` 和携带能力的预定位不依赖摘要权限；Copy 区分本地进度、已确认前缀与可未知的最终结果；WatchName 绑定名字而非某次 publication，跨替换继续存在。主会话另补受限 Boundary 的真实下游衰减责任、Rename 的两侧业务权限/目录循环检查，以及 Query → 读状态 → Ack(旧序列) 的订阅次序。

设计走查覆盖：无 Lookup 权的路径写入；Locate 后拓扑变化且最终请求携带目录授权；只读 grant 跨文件 provider；目标接受数据后 Finish 回复丢失；名字从未发布到 A→B→C 替换；旧 publication 迟到 Withdraw；播放器保留自身摘要并转发 Open。结论是这些路径有明确的返回/交接责任，不需要增加 OAL 对象表、跨 Lookup/Get 身份锁定或通用 tag 写入。该结论是文档和源码依据上的语义复核，不是实现测试或性能证据。
