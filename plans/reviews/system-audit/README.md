# 重写版系统审查

本审查面向当前整棵代码树，不以 diff 或旧实现为边界。目标是证明外部契约、内部设计和实现相互一致，并显式暴露尚无法证明的假设。

## 证据

外部契约的证据层级与使用方式见 `references/README.md`。每项外部语义结论必须引用固定规范的路径与小节；项目内部语义必须引用 `notes/`。`pre-ai` 及旧 review 只用于构造反例和回归问题。

规范没有给出唯一答案时，finding 必须标为设计决策，不得把实现习惯提升为契约。实现参照与规范冲突时，以规范和项目已经确认的设计为准。

## 分片

按依赖顺序审查，每片固定自己的起始 commit：

1. SBI 边界与地址纪律；
2. trapframe、上下文切换与 CSR；
3. 启动、页表与 TLB；
4. SMP、调度与对象生命周期；
5. syscall 与 `shared/` ABI；
6. IPC、FAL 与用户态服务；
7. 工程化收口。

后片可以使用前片已经确认的结论；前片未决时，后片不得把它当作前提。

## 单片流程

### 1. 固定基线

记录 review 开始时的 commit、目标文件和规范版本。完成标准：影响该契约的入口、出口、调用者和共享结构全部进入代码表面。

### 2. 提取契约

从固定规范和 `notes/` 建立契约表，每条包含原文所在文件与小节。完成标准：review 中使用的每个常量、布局、状态转换和地址语义都有来源，或明确标为待决策。

### 3. 映射实现

沿调用关系和状态所有权映射实现，不按目录浏览代替控制流追踪。完成标准：正常路径、错误路径、初始化路径、跨 hart 路径和退出路径均已覆盖。

### 4. 对照审查

逐条尝试证伪契约与实现的一致性。检查重点是遗漏状态、部分保存、错误参数、地址域混淆、溢出、并发可见性和失败语义，而非代码风格。

### 5. 独立核验

由未参与首次审查的 reviewer 核对：

- 规范引用是否支持 finding；
- 代码路径是否真实可达；
- 是否遗漏相邻调用点；
- 建议是否偷偷引入未经确认的架构选择。

没有通过核验的条目保留为“待证明”，不能写成确定 bug。

### 6. 收口

报告使用 `FINDING_TEMPLATE.md`。架构级问题先给选项并由用户拍板；结论可推出的宽泛设计写入 `notes/`。代码修复与报告分开进行，修复后再以该 finding 为 spec 做 diff review。

## 分类

- **缺陷**：存在明确契约违反和可达路径。
- **未证明不变量**：实现依赖某假设，但代码、规范或同步链不足以证明。
- **设计缺口**：外部规范允许多种语义，而项目尚未决定。
- **文档漂移**：`notes/`、注释或 ABI 描述与实现不一致。
- **观察项**：证据不足，保留调查方向但不驱动修改。

严重度与置信度分别记录，不能用高严重度掩盖低置信度。

## 审查纪律

- 一份报告只覆盖一个分片，不把顺手发现的其它层问题展开；跨片问题登记到对应分片。
- 报告呈现当前事实，不记录猜测性的修复历史。
- review 阶段不边看边改；主审先形成自洽报告，再做一次独立核验。reviewer 不充当交互式共同设计器，不以“改一点—审一点”的循环替代主审推导；下一次核验留给完整修复 diff。
- 自动化测试证明样例行为，不替代规范和不变量证明。
