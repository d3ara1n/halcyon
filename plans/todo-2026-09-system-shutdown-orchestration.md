# 系统关机编排设计

> 【未来设计项】设计从用户态决定结束系统，到获准提交最终 `SystemReset` 之间的完整收束政策。

## 问题边界

`SystemReset` 只提供受 capability 授权的最终整机复位动作；它不枚举进程、不通知服务、不等待资源收束，也不判断系统是否适合关机。当前 init 验证负载在固定剧本中监督全部子进程和委托域后提交 reset，只证明该剧本闭合，不等同于通用的用户态优雅退出机制。

本任务负责设计关机意图如何在用户态转化为可证明完成的系统收束。是否存在独立电源管理服务是另一项设计问题，见 [`todo-2026-09-power-management-service.md`](todo-2026-09-power-management-service.md)。两项任务不得互相预设结论。

## 必须闭合的语义

- 关机开始后如何封闭新服务、新委托域与新外部工作的准入；
- 哪些受管对象构成必须收束的范围，以及用户态依据什么终态事实判定范围已经收净；
- 服务如何表达正常退出完成、拒绝、失败或无响应，并让管理者区分这些结果；
- 正常退出的期限、超时后的升级政策，以及强制终止后的资源回收闭包；
- 有状态服务、文件系统与设备停用之间的依赖和顺序如何表达；
- shutdown、reboot 与 system failure 是否采用不同收束政策，紧急故障允许绕过哪些正常步骤；
- 最终提交 `SystemReset` 的许可条件，以及提交失败后系统继续监督或采取其他动作的状态语义。

## 设计纪律

本任务启动前不预设执行主体、服务拓扑、广播或逐级遍历协议、消息格式、超时数值、持久化接口，也不预设 `SystemReset` capability 的分配。设计必须从届时已有的服务编排、文件系统和设备契约自顶向下闭合；发现缺失前置时先立案并重排自然序，不以 init 中增加固定服务名单或逐点通知作为临时答案。

## 触发与完成

在引入首个需要长期运行、持久化状态或设备停用协议的正式系统服务之前，或在系统对外承诺通用优雅关机之前，必须启动本任务。

完成时应形成经确认的 `notes/ideas/` 方向契约、对应实施计划和故障/超时验证矩阵；在此之前，当前 init 剧本只能表述为集成验收政策，不能作为通用关机协议引用。
