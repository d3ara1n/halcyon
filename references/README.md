# 外部参考资料

本目录保存 eRhino 设计、编码和 review 所需的外部资料。它既包含按固定版本取证的硬件、ABI 与协议契约，也包含用于发现候选和比较设计的操作系统资料；不承载 Halcyon 自身的设计决策，项目决策仍以 `notes/` 为准。

## 目录边界

- `normative/`：固定版本的正式规范，是硬件、ABI 与协议结论的首要证据；
- `implementations/`：固定版本的具体实现片段，只用于确认现实中的用法、平台行为和已知边界；
- `systems/`：操作系统、内核和相邻架构的资料索引与专题分析，用于发现方案、比较结构和检查反例，不具有 normative 约束力；
- `INDEX.md`：整个参考资料库的总导航；
- `CONTRACTS.md`：硬件、ABI、协议与固定实现用法的概念定位入口；
- `MANIFEST.md`：已入库上游副本的版本、来源、许可证与裁剪范围。

`systems/INDEX.md` 是内核资料全景清单。未来的逐系统设计分析也放在 `systems/`，以系统名组织，不使用任务或阶段命名。

## 证据层级

1. `normative/` 中固定版本的正式规范；
2. `notes/` 中已经确认的项目设计；
3. 代码中可证明的不变量与测试；
4. `implementations/` 中固定版本的具体实现文档；
5. `systems/` 中的系统设计资料与外部实现分析；
6. `pre-ai` 及其它历史代码，只作为缺陷考古和回归样本。

模型记忆不能单独支持外部契约结论。系统和实现参照不能作为 eRhino 架构选择的独立理由；设计必须从本项目需求推导，再用成熟系统、研究原型和失败案例做对照检查。

## 使用方法

1. 硬件、ABI 或协议问题从 `INDEX.md` 进入 `CONTRACTS.md` 定位固定规范，阅读完整小节及其引用的小节；
2. 系统设计调研从 `systems/INDEX.md` 选择候选，再进入官方文档、源码和论文；
3. review finding 必须引用固定版本文件和小节标题；规范没有明确约束时，结论标为待决策或待证明；
4. 实时仓库和网页只用于发现与初筛。结论进入设计、编码或 review 前，必须固定上游版本，或形成写明版本、日期和证据边界的系统专题；
5. 当前语料不覆盖所需契约时，先从官方一手来源补齐并记录来源，再编写依赖该契约的代码。

目录中的上游正文保持原样；项目解释、采用范围和取舍写入 `notes/`，不直接修改上游副本。

## 版本与采用范围

固定版本是可复现的阅读基线，不等于项目自动采用该版本的全部能力。项目实际支持的 ISA 子集、最低 SBI 版本和必需扩展必须另行在 `notes/` 中成文。

`systems/` 的清单允许跟随上游持续更新；其中的“活跃”或“维护”状态必须注明观察日期。专题分析若支撑具体设计，应记录所用 release、commit、论文版本或文档日期。

## 上游副本更新流程

1. 从官方 release/tag 选择候选版本，阅读 changelog 并确认升级理由；
2. 核对许可证和上游 commit；以完整上游文件替换现有副本，不在副本上打项目补丁；
3. 更新 `MANIFEST.md` 和 `CONTRACTS.md`；
4. 审查新旧规范差异对 `notes/`、代码和测试的影响；
5. 规范升级使用独立提交，避免与功能改动混合。
