# 用户态库的知识归属与依赖

本目录按领域组织可组合的用户态库。全部 Rust 组件先遵守 [`user/README.md`](../README.md) 的统一身份与命名规则；新增库、调整公共类型、修改依赖或组装服务前，再按本篇判断知识归属。领域设计由 [notes/ideas/framework.md](../../notes/ideas/framework.md) 及其链接的专题文档拥有；本轮迁移过程与验证见[库知识归属、依赖、目录与命名档案](../../plans/archived/todo-2026-09-21-library-knowledge-ownership.md)。

## 按领域组织

一个库集中拥有一个领域的概念、类型、契约与可复用机制。管理接口与消费接口可以同属一个领域库，按角色提供不同接口；不按调用者是不是系统服务、是否持管理权拆出相互重复的知识库。framework、client、server 等使用方式不替代领域归属；`libruntime` 的独立领域是 Rust 程序环境，不承担通用执行或其它库的资源入口。

库提供知识与实现，capability 决定可操作的对象及权利，进程通过组合库、授权与业务承担运行角色。链接一个库不产生权限，也不自动启动该库涉及的全部运行角色。普通进程可以使用进程领域类型和查询接口；pm 组合服务框架与进程领域库，并凭实际取得的控制能力承担管理职责。

公共类型保持唯一真值。内核 ABI 定义的 Pid、对象角色与 rights 可以由用户库封装或重导出，不为领域划分复制底层定义；用户态领域类型与政策则由相应领域拥有。

## 依赖方向与知识收敛

依赖从知识的使用者指向提供者，形成有向无环图。上层使用下层的通用概念表达自身领域，下层不为上层预定义领域类型、状态或资源分类。依赖审视既检查 Cargo 图，也检查公共类型、回调契约、资源枚举和调用顺序要求，不能只以“没有包循环”证明分层正确。

- `libbudget` 拥有账户、领域计费视图、额度、预留、扣账和退款；`libexecution` 拥有任务推进、来源观察、期限、唤醒、停止与退休。二者不解释服务角色或业务资源。
- `liboal` 拥有开放发现表示、Boundary、Namespace 和客户端路径接续；不定义文件种类、服务记录、共同 ACL 或 backing。
- `libfs` 拥有文件协议、纯值、FsRights、文件 backing、provider 支持及客户端 Copy 组合。Copy 通过 OAL 接续、RPC 调用和 Runnel 搬运持有具体会话/清理责任，由使用侧 init 任务族组合运行；库不自建运行体，不依赖原 FAL，也不持服务目录投影。
- `libservice` 拥有服务描述、发布授权、注册/取得、控制与生命周期；只依赖 OAL 的发现和接续表达，直接从 registry backing 生成视图，不依赖文件库或文件节点。
- 原 `libfal` 已删除；普通文件与服务客户端直接消费各自领域协议及 OAL Namespace/walk，没有 DirectoryGrant/Position 兼容出口。
- `librpc` 拥有请求回复、调用生命周期及带序号确认的订阅客户端会话；领域通过静态 Protocol 提供自己的编解码和快照投影，RPC 不解释文件或服务事件。`librunnel` 拥有流协议，`libprocess` 拥有进程领域能力。它们可以直接消费公共执行和记账，不反向依赖 `libservice`。
- 驱动公共知识的正式库名是 `libdriver`，设备领域库名是 `libdevice`；当前没有真实公共驱动机制，因此不保留空库占位。
- `libkernel` 拥有用户态内核调用与资源的安全封装；`libruntime` 组合 `libprocess::context`、`libthread` 和 libkernel 完成程序环境职责，但不复制这些知识或成为其通用 facade。其它领域/机制库不得反向依赖具体 runtime，程序直接使用知识 owner 的 API；库使用 core/alloc，不选择具体 global allocator。链接只复用知识，不授予 capability，也不自动启动线程、IPC 接收器或服务。完整边界由 [framework](../../notes/ideas/framework.md) 拥有。

领域知识收敛不要求把整条调用链搬到一个库。服务描述的完整性和生命周期由服务领域负责，消息投递由运输层负责。改变服务规则不应要求这些下层同步理解新的服务含义。

## 公共机制有独立归属

通用记账由 `libbudget` 独立拥有。一个非领域化 `Account` 表示唯一付款身份；`BudgetSlot` 由具体预算布局签发，`AccountView<K>` 只把同一身份绑定到该布局的领域资源类别，跨布局绑定会被拒绝，视图克隆不新建账户、分配映射或额度。需要共同上限的类别绑定同一个实际额度；节点数、任务数和字节等不同单位分别约束。长期 owner 保存非泛型 Charge，包括零单位占用也持续保活账户名额；退款跟随实际释放或已提交的占用缩减。底层 `Counter`、`Permit` 与组合扣账原语仍由 shared 的 `metadata_admission` 唯一拥有。
`AllocatorBacked`也由libbudget拥有：用户共享容器显式选择该Funding策略，表示本层不追加逐分配软额度，由程序选定allocator供给。既有领域Charge仍约束其业务占用；该策略不宣称Kernel metadata已付款，不选择libruntime或allocator实现。需要严格逐存储收费时由领域选择字节类别并接AccountView，不能以单位默认值冒充该合同。

通用执行由 `libexecution` 独立拥有，包括任务推进、观察来源、期限与唤醒。执行定义自己的资源类别并消费执行领域账户视图，不借用 FAL 或服务的枚举和裸槽位；非服务消费者可直接使用该库。

跨领域组合位于知识的使用侧。通用接口可以接受行为或依赖，但其契约不能暗含上层服务身份、状态或政策；不得通过回调、重新导出或集中 facade 隐藏反向依赖。

账户余额、传输身份和领域 capability 分别表示付款、认证与授权。可信装配建立付款绑定；派生 grant、sender 别名与领域视图克隆继承原账户，不重新开户。多项预留由准备对象持有并在失败时完整回滚，取消或撤销可见性不提前释放仍由真实 owner 占用的额度。

## 组合与变更门

进程按所需职责选择库：服务框架与进程能力可组合成 pm，普通应用可仅使用进程能力，直接取得 endpoint 的调用者可仅使用相应协议。新增领域能力不得迫使无关消费者采用一整套服务装配。

每次归属调整须明确唯一知识 owner、真实消费者、依赖方向与失败/退出/退款责任，同时迁移公共类型和调用点。通用机制抽出后删除旧位置及兼容出口；不能仅改包名或搬目录而保留原来的语义倒置。目录、Cargo 身份和引用路径按 [`user/README.md`](../README.md) 的命名纪律同步，实施与验证证据记入唯一专题计划。
