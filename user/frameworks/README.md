# 用户态库的知识归属与依赖

本目录按领域组织可组合的用户态库。新增库、调整公共类型、修改依赖或组装服务前，先按本篇判断知识归属。领域设计由 [notes/ideas/framework.md](../../notes/ideas/framework.md) 及其链接的专题文档拥有；本篇规定库组织与施工纪律，当前迁移由 [库知识归属与依赖重排计划](../../plans/todo-2026-09-21-library-knowledge-ownership.md) 承接。

## 按领域组织

一个库集中拥有一个领域的概念、类型、契约与可复用机制。管理接口与消费接口可以同属一个领域库，按角色提供不同接口；不按调用者是不是系统服务、是否持管理权拆出相互重复的知识库。runtime、framework、client、server 描述实现或使用方式，不替代领域归属。

库提供知识与实现，capability 决定可操作的对象及权利，进程通过组合库、授权与业务承担运行角色。链接一个库不产生权限，也不自动启动该库涉及的全部运行角色。普通进程可以使用进程领域类型和查询接口；pm 组合服务框架与进程领域库，并凭实际取得的控制能力承担管理职责。

公共类型保持唯一真值。内核 ABI 定义的 Pid、对象角色与 rights 可以由用户库封装或重导出，不为领域划分复制底层定义；用户态领域类型与政策则由相应领域拥有。

## 依赖方向与知识收敛

依赖从知识的使用者指向提供者，形成有向无环图。上层使用下层的通用概念表达自身领域，下层不为上层预定义领域类型、状态或资源分类。依赖审视既检查 Cargo 图，也检查公共类型、回调契约、资源枚举和调用顺序要求，不能只以“没有包循环”证明分层正确。

- `libsrv` 拥有服务领域的声明、提供、使用与生命周期知识，可以消费 FAL、RPC、进程及公共机制的接口。
- `libfal` 拥有通用目录、节点、Record/Handle 值、授权和 FAL 协议；`libsrv` 可用 Record 表达 ServiceRecord，`libfal` 不定义 ServiceRecord 或服务状态供上层消费。
- `librpc` 拥有请求回复及调用生命周期，`libfs` 拥有 namespace 与路径访问，`librunnel` 拥有流协议，`libprocess` 拥有进程领域能力。它们的成立不以服务框架为前提，不能反向依赖 `libsrv`。
- `rinlib` 拥有程序基础运行环境与内核契约的安全封装，启动 payload 的用户态领域语义由上层解释。内核、共享 ABI 与 `rinlib` 不拥有服务概念；下层出现服务专用结构必须重新判断归属。

领域知识收敛不要求把整条调用链搬到一个库。服务记录的完整性和生命周期由服务领域负责，Record 编码由 FAL 负责，消息投递由运输层负责。改变服务规则不应要求这些下层同步理解新的服务含义。

## 公共机制有独立归属

通用记账是独立知识领域，必须有专门的库拥有账户、额度、预留、扣账、退款及其不变量。执行库和领域库消费记账接口；记账不附属于服务框架或执行运行体。领域资源种类、授权来源和额度政策由对应领域或组合装配提供，公共记账不枚举 ServiceRecord、文件节点等业务类别。

任务推进、观察来源、期限与唤醒等通用执行机制同样应有清晰的独立归属。它们不因首个消费者是服务而归入服务领域，也不要求非服务消费者引入服务框架。公共机制的具体包名、跨层位置和组合接口根据真实消费者确定，不建立无独立职责的转发包。

跨领域组合位于知识的使用侧。通用接口可以接受行为或依赖，但其契约不能暗含上层服务身份、状态或政策；不得通过回调、重新导出或集中 facade 隐藏反向依赖。

## 组合与变更门

进程按所需职责选择库：服务框架与进程能力可组合成 pm，普通应用可仅使用进程能力，直接取得 endpoint 的调用者可仅使用相应协议。新增领域能力不得迫使无关消费者采用一整套服务装配。

每次归属调整须明确唯一知识 owner、真实消费者、依赖方向与失败/退出/退款责任，同时迁移公共类型和调用点。通用机制抽出后删除旧位置及兼容出口；不能仅改包名或搬目录而保留原来的语义倒置。目录、Cargo 身份和引用路径按项目命名纪律同步，实施与验证证据记入唯一专题计划。
