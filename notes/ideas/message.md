# 消息

消息是 IPC 的**控制面**：一种单向、进程到进程或内核、非阻塞投递的通信方式，承载服务请求/应答等小批量数据。三面分工：小数据走消息，大块流式数据走隧道（[tunnel](tunnel.md)），事件通知走信号（[signal](signal.md)）。

## 消息与邮箱

一个消息包含发送者、类型和负载：

- **类型**（kind）：由通信双方的上层协议约定，内核不解释；
- **负载**：字节序列，长度上限为固定常量（量级为一个消息槽，具体值随实现定）；
- **发送者**（sender）：由内核填写，接收方不可伪造来源。

每个进程拥有一个**有界邮箱**：FIFO 序，容量 N 条（N 为可调常量）。邮箱是内核对象，负载在投递时由内核拷贝入箱、接收时拷出到接收方缓冲区——投递完成后双方内存即解耦，不存在共享生命周期问题。

## 系统调用语义

| 调用 | 语义 | 阻塞性 |
|------|------|--------|
| `Send(target, kind, payload)` | 将目标/类型/负载一次性投入目标邮箱 | **永不阻塞** |
| `Peek(digest_buf)` | 检查队头消息，得摘要（sender/kind/负载长度）；不动邮箱状态 | 非阻塞 |
| `Receive(buf)` | 取队头消息负载拷入 buf；空箱时可阻塞等待于邮箱对象 | **允许阻塞** |
| `Discard()` | 抛弃队头消息 | 非阻塞 |

失败语义统一走错误码（a0=错误码/a1=结果，见 [call](call.md)）：

- 邮箱满：`Send` 立即返回 `MailboxFull`。发送不阻塞是有意为之——若发送方可被卡死，接收方只需停止 Receive 就能反过来钳住所有对端；可用性由发送方自留，流控是上层协议的事。
- 邮箱空：`Peek`/`Discard` 返回 `ObjectNotAvailable`；`Receive` 提供阻塞形态（见下）。
- 缓冲不足：`Receive` 的 buf 小于负载长度则 `IllegalArgument`——长度可先经 `Peek` 获得。

### Receive 的阻塞形态

面向服务的消费循环，`Receive` 在空箱时**阻塞等待**而非返回错误：

- 线程作为等待者加入**邮箱对象的等待者队列**（FIFO，见 [signal](signal.md) 的状态机），转 Waiting；
- 消息入箱即移交事件：队头等待者被定向唤醒，Receive 取得消息，结果直写执行现场——与 sleep 异步通路完全同构，内核不等待。

不需要忙轮询，也不引入第三种等待机制；消息唤醒与信号唤醒是同一个机制。

## 到达通知

消息成功入箱即在邮箱对象上产生一个 `NONEMPTY` 事件（状态机见 [signal](signal.md)）：

- 已有线程阻塞在该邮箱上 → 事件直接移交队头等待者，定向唤醒；
- 无人在等 → `NONEMPTY` 进入粘滞余量，之后的 Peek/Receive 立即可见。

轮询型与阻塞型消费者因此是同一到达事件的两个消费面，不是两种投递模型。

## 典型形态：服务主循环

系统服务（fs/pm 等）以消息为请求入口，标准形态：

```text
loop {
    digest = receive()            // 阻塞等待下一请求
    match digest.kind {
        REQ_X => do_x(); reply_to(digest.sender)
        REQ_Y => do_y(); reply_to(digest.sender)
        ...
    }
}
```

请求-应答配对天然形成流控：客户端发出下一条请求前必须等到上一条应答，单客户端不可能灌爆服务邮箱。多客户端并发超出容量时，超出者收到 `MailboxFull` 并自行择机重发——这是可观测、可控的降级路径，不是静默丢包。

## 内核作为消息终点

`Pid=0` 定向内核邮箱：`Send(0, kind, payload)` 行为同普通投递。这是面向未来的入口预留（如内核调试通道、内核侧服务请求面），当前无消费者；契约先行，行为面与普通邮箱一致。

## 边界

- **消息不转移所有权**：不携带能力/句柄，不传递任何对象的内核级引用；需要转授的对象（如隧道 key）由上层协议在负载中自行编码，其访问控制不属于消息层的职责。
- **不保证有序跨对全局**：FIFO 序仅在单个邮箱内成立，不同发送对的交错顺序不作承诺。
- **负载大小有界**：超过一个消息槽的数据必须走隧道，消息层不做分片重组。
