# 用户态内核接口与资源所有权

libkernel 拥有内核调用、安全资源表示和单次操作的责任转移。它不拥有程序语言环境、业务执行循环或服务政策。库的组合关系由 [framework](framework.md) 拥有，对象与 Close 的基础关系由 [object](object.md) 拥有。

## 接口层次

私有调用后端处理寄存器、调用号与结果交付；安全资源接口表达构造、借用、消耗、转换和观察。必要的原始接管跨显式 unsafe 边界。领域库在其上组合进程、线程、RPC、文件与设备能力。

共享 ABI 拥有固定宽表示；用户封装不建立第二份调用号、权限或错误定义，也不通过统一 facade 隐藏知识的反向依赖。

## 值、借用与 owner

Handle 数值和描述可以复制，真实持有与关闭责任不能由此复制。安全 owner 从创建、受权派生、接收或可信启动交付中取得；从裸数值恢复 owner 必须证明独占责任。

借用允许操作已有资源，不授予消费或额外关闭权。类型化视图可以约束对象关系与所需权限，但内核仍独立检查每次 authority。映射借用还约束内存访问的有效期，不能通过通用资源包装绕过。

## 消耗与失败形状

资源创建、修改、转移与业务提交各自表达真实的提交边界。未提交失败保留原 owner；已经完成转移不能伪装成仍在调用者本地的输入。结果不确定性与资源处置责任分别保留。

合法 Close 是本地持有的必成释放：有界完成失效与责任交接，普通 Drop 不等待完整退休、对端或业务结果。物理资源在内核的安全退休条件达成后才可复用。

Unmap 等访问撤销屏障，以及上层 Finish/Flush 等业务完成操作有独立含义；它们不能被 Close 的成功代替。需要明确完成结果时由调用者显式发起观察或等待，不为每次释放自动创建用户可见事务。

## 分配、停驻与取消

用户堆分配、内核资源准入和等待是不同维度。接口使调用者能够区分本地释放、可拒绝请求和显式完成等待；基本调用不要求启动特定 runtime 或服务循环。

调用者放弃结果或终止，不撤销内核已提交的责任。需要跨越等待的资源与结果由完整 owner 持有；上层不编排内核清理游标，也不因内部暂忙建立 Close 重试任务。

## 模块出口与独立事实

libkernel 提供对象授权、内存与映射、任务原语、IPC、等待、时间、启动 view 和系统控制。装载、监督、线程语言环境、请求应答、路径访问和设备政策由各领域库拥有。

Process/Thread 控制能力只表达管理和观察，不隐含用户栈或业务结果的所有权。进程终止后的回收由内核自动完成；监督封装不再提供维持回收活性的 Drain 循环。
